# 欢匠·序流排队分诊管理系统 - 数据库设计说明书

> **文档位置：** `docs/database/` · 表结构变更请同步更新本文档与 [SCHEMA_NAMING.md](SCHEMA_NAMING.md)。

## 一、 引言

本节定义了“欢匠·序流排队分诊管理系统 (PDJH-Server)”的核心底层关系型数据库（RDBMS）的架构与设计标准。本系统主要基于 MySQL 8.0+ 构建，利用 InnoDB 引擎的行级锁与事务隔离特性，确保在医疗早高峰阶段的万级并发下，队列业务数据的强一致性与业务防重防串。

---

## 二、 命名规范与全局设计理念

1. **库表字符集**：系统全量表及字段均要求使用 `utf8mb4`及 `utf8mb4_general_ci` 排序规则，以兼容医疗系统可能出现的生僻字与特殊表情符号。
2. **命名约束**：
   * 表名与字段名均采用下划线（Snake Case）命名法，如 `call_list`，并全部使用小写（通过 `lower_case_table_names=1` 规避系统大小写敏感故障）。
3. **主键与索引策略**：
   * 业务核心流转表（如排队记录表）采用 `AUTO_INCREMENT` 数值型主键，提升 InnoDB 聚簇索引的分页性能。
   * 档案字典模型表（如科室、医生表）采用 36 位/64 位 `UUID` 或业务 String 型主键，便于多院区分布式主备库的数据合并。
   * 高频查询与聚合条件均覆盖组合索引（例如针对 `log_type` + `create_time`）。

---

## 三、 核心概念与实体关系模型 (ER 概述)

系统的实体流转以 **患者 (Patient / CallList)** 和 **业务节点 (Department / Doctor)** 为核心，辅以 **医技检查项 (ExamRecordDetail)** 构建依赖关联图谱。

* 一个科室 (Department) 包含多名 医生 (Doctor)。
* 一个出诊医生 (Doctor) 可绑定至一个 物理大屏 (DocScreen)。
* 每名患者根据其业务单据 (HIS 入列) 会生成一条 排队实体 (CallList)，由引擎动态调度分配到 科室 或直接到 医生 队列中。
* 对于复杂的医技依赖体检，将生成多条串/并行的 体检明细 (ExamRecordDetail) 用于状态监控验证。

## 四、 核心数据表结构字典

### 1. 核心排队呼叫表 (`call_list`)
**用途：** 动态追踪每个患者从挂号、签到、排班、呼叫、就诊到最终完结（或被过号）的全链路生命周期状态。本表是 Triage Engine (智能分诊引擎) 进行核心锁操作与逻辑计算的基底。

| 字段名 (Field) | 类型 (Type) | 约束 | 描述 (Comments) |
| --- | --- | --- | --- |
| `id` | INT | PK, AUTO | 内部自增流水主键 |
| `patient_code` | VARCHAR | | 患者唯一就诊标识号/条码 |
| `patient_name` | VARCHAR | | 患者姓名（对接或播报所需） |
| `call_status` / `state`| INT | | 队列流转状态: 0=等待中, 1=已呼叫, 2=已就诊, 3=已过号 |
| `dept_id` / `deptCode` | VARCHAR | | 派发的科室标识 / 外键关联 `department` |
| `doctor_id` | VARCHAR | | 被指派的接诊医生标识（若为空表示在公共池） |
| `call_number` / `show_no`| VARCHAR | | 用于大屏显示的呼叫号码（如 A001） |
| `is_priority` | INT | | 紧急或优抚特权标识（1=优先插队, 0=平级排队） |
| `is_appointment`| INT | | 标示是否为线上严格预约锁号的患者（1=是, 0=否） |
| `triage_state` | VARCHAR | | 分诊微服务引擎扩展状态 (如 WAITING, REVISIT, PASSED) |
| `call_count` | INT | | 历史被呼叫的次数累计（用于判定多次空呼则过号放弃） |
| `check_in_time` | DATETIME | | 二次到院报到/扫码签到真实动作发生的时间戳 |
| `start_time` | DATETIME | | 实际开始接诊时间（计算 SLA 性能等候时长） |
| `source_type` | VARCHAR | | 就诊溯源：普通门诊、医技、体检或药房取药 |

### 2. 科室与业务大类档案表 (`department`)
**用途：** 管理全院各物理与虚拟排队节点的结构树，以及科室被紧急切流与熔断时的控制面板状态。

| 字段名 (Field) | 类型 (Type) | 约束 | 描述 (Comments) |
| --- | --- | --- | --- |
| `id` | VARCHAR(36)| PK | 科室全局唯一主键 |
| `name` / `dept_name` | VARCHAR(100)| | 科室人类可读名称（例如“呼吸内科一区”） |
| `father_id` | VARCHAR(36)| | 父科室或统筹区域 ID，构成级联树结构 |
| `business_type` | VARCHAR(50)| | 业务宏观分类: OUTPATIENT, PHARMACY, LAB, EXAM |
| `med_tech_sub_type` | VARCHAR(20)| | 医技科室子类型（针对 EXAM/LAB 进行深入路由时使用） |
| `is_suspended` | INT | DEFAULT 0 | 危控状态标识：1=被人工熔断挂起宕机, 0=正常流通 |
| `queue` | VARCHAR(50)| | 可分配的外部显示或独立队列别名约束 |

### 3. 医生医护档案表 (`doctor`)
**用途：** 全院医生唯一主数据，含业务出诊信息与展示档案（原 `screen_intro` 已合并废弃）。

| 字段名 (Field) | 类型 (Type) | 约束 | 描述 (Comments) |
| --- | --- | --- | --- |
| `id` | VARCHAR(64)| PK | 全局医生唯一 ID |
| `work_no` | VARCHAR(50)| | 卫计委或院内通用工号 |
| `name` | VARCHAR(50)| | 姓名全称 |
| `gender` | VARCHAR(10)| | 性别 |
| `title` | VARCHAR(50)| | 资历及职称类别（主任医师等，影响排队优先权重） |
| `dept_id` | VARCHAR(64)| | 所属或今日挂靠的出诊科室 ID |
| `specialty` | VARCHAR(500)| | 擅长/专长描述 |
| `remarks` | VARCHAR(500)| | 医生简介（展示用） |
| `avatar` | VARCHAR(255)| | 头像路径（如 `/uploads/intros/xxx.png`） |
| `display_status` | INT | DEFAULT 1 | 展示档案：1=启用 0=冻结（与出诊状态分离） |
| `screen_id` | VARCHAR(64)| | 该医生目前物理所处位置连接的门口播报大屏 ID |
| `office_name` | VARCHAR(100)| | 实体门牌号信息（例如“内科四诊室”） |
| `is_on_duty` | INT | DEFAULT 1 | 强排班判定字段：1=出诊接单中, 0=停诊休息 |
| `create_date` | DATETIME | | 建档时间 |

### 4. 医技体检项目拆分调度表 (`exam_record_detail`)
**用途：** 用于在超声、胃肠镜及并行体检场景时，依据业务拆分维度，精确把控病患在多项并行项目中各项流程的完结与阻滞情况。

| 字段名 (Field) | 类型 (Type) | 约束 | 描述 (Comments) |
| --- | --- | --- | --- |
| `id` | INT | PK, AUTO | 自增流水主键 |
| `patient_code` | VARCHAR | | 溯源病患标识 |
| `exam_batch_no` | VARCHAR | | 并行体检的大批次号/套餐组合订单号 |
| `item_id` / `item_code`| INT/VARCHAR | | 具体的细分体检项目 ID (如对应生化全套) |
| `state` | INT | | 子项目运转状态 (0=未做, 1=队列中, 2=进行中, 3=已完结) |
| `enqueue_time` | DATETIME | | 进入子分类排队池时间戳 |
| `complete_time` | DATETIME | | 通过事件源钩子回调确以完成的时间发生点 |

### 5. 系统核心审计日志表 (`sys_action_log`)
**用途：** 作为系统操作与业务动作的可回溯凭证存根核心，用于运维工程师的错误排查，或在产生医疗排队纠纷时用以取证。

| 字段名 (Field) | 类型 (Type) | 约束 | 描述 (Comments) |
| --- | --- | --- | --- |
| `id` | BIGINT | PK, AUTO | 百万乃至亿级防堆叠流水日志序列 |
| `log_type` | VARCHAR(30)| IND | 审计分类界限: VOICE_BROADCAST, DOCTOR_CALL, 等 |
| `operator` | VARCHAR(100)| | 导致状态流转的动作发起方（医生、后台控制员等） |
| `action_desc` | VARCHAR(500)| | 具有高语义的人类直读短记录（如: "张医师强通抢单"） |
| `payload` | TEXT | | 发起核心指令时的底层 JSON 数据快照 |
| `is_success` | BOOLEAN | | 后端引擎动作链路执行结果闭环状态确认 |
| `error_message` | TEXT | | 故障产生时的 Java / 引擎报错堆栈详细录入 |
| `create_time` | DATETIME | IND | 触发时间戳（具备高精复合索引特性） |

## 五、 DDL / 架构迁移规则设定 (Schema Migration)

系统已默认启用 Hibernate / Spring Data JPA 的前沿元数据验证特性。
* 在生产环境部署或横滑迁移下，推荐关闭 JPA 的建表指令 (`spring.jpa.hibernate.ddl-auto=none`)。
* 数据库 Schema 的迭代与表字段升级需统一由外置维护脚本（或 Flyway / Liquibase 组件）负责执行控制，借此严防因框架过度反射（Reflection）引发的数据表丢失或毁坏风险。
