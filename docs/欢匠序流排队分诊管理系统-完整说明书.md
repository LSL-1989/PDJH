# 1. 产品定位、愿景与用户画像

## 1.1 要解决什么问题

医疗机构门诊、药房、医技、体检场景普遍存在：

- 患者不知道去哪间诊室、还要等多久、自己是不是被过号。
- 现场秩序依赖人工喊号，空号、插队、复诊回流难以公平处理。
- 医生操作被 HIS 界面占满，叫号动作必须极简、可悬浮、不抢焦点。
- 护士台需要应急干预（代签到、复活、插队、转诊、停诊），但不能代替医生叫号。
- 院长/主任需要看见排队热力、过号率、SLA 超时，而不是事后翻表。
- 医院 HIS/LIS/PACS 异构，对接方式必须能在「有标准 API / 只能 Webhook / 只能读库 / 内网物理隔离」四种院情下落地。

本系统定位为医院门诊与医技科室的**排队调度枢纽**：把无序人流变成按规则、可干预、可播报、可审计的数字工作流。

## 1.2 三类用户与核心诉求

| 用户层 | 角色 | 核心诉求 | 主要使用端 |
|--------|------|----------|------------|
| C 端体验层 | 患者、家属 | 明指引、少等待、少跑错门 | 自助签到机、候诊大屏、门边屏、体检 H5 |
| B 端操作层 | 医生、护士、药师、检验窗口 | 简操作、强管控、可应急 | 叫号器、护士工作站 |
| M 端决策层 | 门诊/药房/体检/医技主任、院办、信息科 | 保秩序、优效能、可配置、可追溯 | 管理后台主任工作台、院长看板、规则中心、集成网关 |

## 1.3 产品能力边界

**系统做：**

- 挂号/缴费后的入队、签到、叫号、过号、复诊、完成。
- 按物理诊室/窗口调度，驱动候诊大屏、门边屏、独立音响。
- 护士应急干预与全流程留痕。
- 体检项目依赖图谱上的自动派下一站。
- HIS 多协议接入与配置级回滚。

**系统不做（或明确不替代）：**

- 不替代 HIS 挂号收费、电子病历、处方、检验报告本身。
- 门边屏**不发起/不操作叫号**（无叫号按钮、不抢叫号权），不做签到、不做触摸配置；但可作为**播报终端**，在开启「本地叫号开关」时本地 TTS 播报叫号内容（见 §18.6）。
- 护士站不代窗口「呼叫下一位」（干预队列，不抢叫号权）。
- 候诊大屏不承担单诊室门口确认「进对门」的职责（由门边屏承担）。
- **加号/限号决策与号源池不在现状范围**：医生/护士为患者“突破号源上限加号”、号源池管理、加号费用收补**现状未实现**——`EmergencyOverride` 仅做队列内插队；`doctor_schedule.max_quota`（§9.7）只是登记号源上限、无拦截执行。如需支持，按 **§4.8「加号与限号（设计项）」** 蓝图落地；未落地前，加号由 HIS/现场人工放号后按普通入队进入本系统（放号本身不收费、不占本系统号源）。

## 2.3 三层绑定原则（诊区 / 诊室 / 当日坐诊）

系统把「排队业务」和「门口硬件」拆开，避免医生轮换时改硬件绑定：

```
诊区/科室 department     → 管排队、分诊、统计（医生可轮换）
物理诊室 office_room     → 管门牌、门边屏、签到机覆盖范围（位置固定）
当日坐诊 doctor_schedule → 管「今天谁在哪间诊室」（按日可变）
排队单   call_list       → 运行时同时记下 dept_id + office_room_id + doctor_id
```

结论：

- **门边屏绑定物理诊室**，不绑定科室、不绑定医生。
- **签到机绑定若干物理诊室**，只能核销这些诊室上的待签到单。
- **候诊大屏绑定若干诊室或科室**，汇总这些范围内的叫号。
- 医生跨诊区出诊时改排班的 `dept_id` + `office_room_id`，门口屏自动显示当日该室医生。

## 2.5 屏幕多角色复用（门诊候诊 / 药房窗口 / 检验窗口，设计项）

角色与 `terminal_type=SCREEN` 配合；CLINIC 门边屏不受影响。

### 2. 角色切换与关联联动（后台）

- 屏幕管理新增「屏幕角色」下拉；**选角色 = 自动设置 `template_route` + 校验关联范围类型**（门诊 → 科室/诊室；药房窗口 → PHARMACY 窗口；检验窗口 → LAB 窗口）；
- 切换角色时关联范围不匹配（如门诊角色下绑了药房窗口）→ 保存拦截并提示；
- 保存后壳下次 `Resolve` 返回新 `templateRoute`，刷新即切换（同 §17.1 绑定流程）。

### 3. 数据与展示差异

- 数据同源：`CallList/GetCallListInput` 按设备解析允许诊室后查队列（§11.9），窗口屏关联到药房/检验窗口即拉到对应队列（`source_type=PHARMACY` / `OUTPATIENT_EXAM`）；
- 药房窗口屏：`PREPARING` 配药中（灰显）、`WAITING` 请取药（高亮）、当前取药号（state=1）；
- 检验窗口屏：采血队列 + 当前呼叫（state=1）；
- 语音：`call_content` 按角色提示配置（取药/采血叫号文案），`voice_channel` 可绑独立音响或本机 TTS。

### 4. 边界

- **一屏一角**：同一时刻一块屏一个角色（terminal_type + template_route 决定）；切换 = 后台改角色，壳刷新生效；
- 叫号仍由叫号器（`PharmacyDeskWindow` / 检验窗口）发起，屏只展示 + 可选播报，**不抢叫号权**；
- 可选增值（需另行评估）：窗口屏模板可提供触摸「呼叫下一位」，属叫号能力延伸到屏（与「门边屏不做触摸配置」无关，该边界仅针对门边屏）；
- 屏幕方向由模板适配（门诊横屏、窗口屏可竖屏）。

## 2.6 终端样式模板体系与工程部署边界（设计项）

**目标：** 候诊大屏、门边屏、自助签到机均可配置多种**样式模板**；模板只改外观与版式，不改变业务逻辑。

# 3. 产品需求：四大就诊场景与四条调度模型

「排队叫号」在本产品里不是一套算法套所有科室，而是四条本质不同的调度模型，与四大就诊场景一一对应：

| 场景 | 调度模型 | 章节 |
|------|----------|------|
| 综合门诊分诊 | 线性单队列 | 3.1 |
| 药房发药 | 池化分窗 | 3.2 |
| 门诊医技检查 | 并联独立队列 | 3.3 |
| 综合体检导检 | 图路径规划 | 3.4 |

## 3.1 综合门诊分诊 — 线性单队列

**场景：** 患者挂号取号，进入指定科室/医生/诊室队列，按顺序叫号进诊室。路径一次性：取号 → 等候 → 叫号 → 就诊 → 结束。

**谁决定下一站：** 诊室固定，系统按队列顺序。

**核心规则需求：**

| 业务问题 | 配置项 | 默认 | 说明 |
|----------|--------|------|------|
| 叫到多久没来算过号 | `callTimeoutMin` | 5 分钟 | 定时任务扫描待诊超时 |
| 过几次彻底踢出 | `maxSkipCount` | 3 次 | 未达上限则重排末位 |
| 复诊回流权重 | `revisitPriorityWeight` | 2 | 当天已就诊再进队列 |
| 老人/优抚优先 | `elderPriority` | 开 | 开关 |
| 急诊是否可插队首 | `emergencyInsert` | 开 | 开关 |
| 预呼叫人数 | `preCallCount` | 3 | 大屏「请准备」 |
| 到第几位发提醒 | `smsAdvanceCount` | 3 | 需通知渠道开启 |
| 排序权重模型 | `priorityModel` | 权重表（**设计项**） | 多因子权重（预约/急诊/军人/老人/复诊/危急）参与排序 = 权重降序 + 入队时间升序（R-1，见 §10.1；现状排序见下表图例） |
| 过号重排位置 | `requeuePosition` | `END` | 队尾 / 队首 `FRONT` / 按原序 `BY_TIME`（R-2） |
| 预约时段穿插 | `appointmentSlotQuota` | 6 预约 + 4 现场 | 每时段预约/现场配额（R-3） |
| 预呼叫提前量 | `preCallAdvanceMin` | 5 | 预呼后 N 分钟未正式叫号再重呼（R-4） |
| 一次叫号人数 | `simultaneousCallCount` | 1 | 一次叫几人（R-7） |
| 最长候诊预警 | `maxWaitWarnMinutes` | 60 | 超过后护士站/看板告警（R-11） |

**产品能力：** 顺呼、重呼、过号、完成、点名呼叫、诊室切换、二次扫码签到、预约时段拦截、迟到剥夺预约优先。

> **口径与图例：** 本表混排「现状键」与「设计项键」——标注 `（R-x）` 或“设计项”的条目为对标补齐的设计项（差距分析附录 C），**不作为现状验收项**，落地以代码为准；未标注项以 §10.1 与代码为准。**排序现状口径（P0-3 统一）：当前排序以入队/签到时间升序为基础，叠加现状已有的规则性优先——复诊优先（`revisitPriorityWeight`）、老年/优抚优先（`elderPriority`）、急诊插队（`emergencyInsert`）及护士/医生手动插队（`ManualCutIn`/`EmergencyOverride`）；`priorityModel` 统一权重表与 `call_list.priority_weight` 列为 R-1 设计项（§9.1/§10.1 同口径），尚未落地。**

## 3.2 药房发药 — 池化分配

**本质：** 分配的是处方到窗口，不是患者到固定医生。

**路径：** 开方缴费 → 药房扫码签到建单（`PREPARING` 配药中）→ 配药完成（`WAITING`）→ 窗口叫号取药。

**与门诊关键差异：**

- 门诊先有 HIS 推送的 `UNARRIVED` 单，签到是核销；药房常常是扫码才建单。
- 药房超时发生在**药已备好患者不来取**，不是叫号无人应答。
- `PREPARING` 不可叫号，只有 `WAITING` 可叫。

**规则：** 等候超时、窗口分流算法（最短队列/轮询/按药品类型）、急诊窗、中西药分窗、积压阈值、催取药提醒、**超时后处理** `overdueAction`（保留 / 自动作废并通知 / 二次催取后作废，R-13，见 §10.1）。**叫号应答超时**（叫到号无人来取，`callTimeoutMin`）与**分窗/优先判定输入来源**（扫码/HIS 药品大类，无输入回退最短队列）见 §10.1 RULE_PHARMACY 注。

## 3.3 门诊医技检查 — 并联独立队列

患者拿检查单自行去检验/超声/放射/心电，**各科独立排队，系统不替患者决定顺序**。这与体检导检（系统推下一站）完全不同。

| 医技子类 | 服务形态 | 典型规则 |
|----------|----------|----------|
| 检验采血 | 多窗口、服务短、空腹高峰 | 分窗、空腹优先、急诊优先、一人多管合并 |
| 超声 | 检查时长 10–30 分钟 | 预约+当日混合、按探头分室、空腹优先 |
| 放射 CT/MRI | 设备贵、必须限流 | 时段配额、造影等待区、危急值 |
| 心电图 | 5–8 分钟、可并联多床 | 急诊 10 分钟绿色通道、Holter 分流 |

检验签到：扫码入队并分窗，**直接 `WAITING`**（无配药环节）。HIS 若已推 `UNARRIVED` 到本机绑定窗口则核销不新建。

## 3.4 综合体检导检 — 图路径规划

患者套餐含多项检查，项目之间有依赖（如腹部彩超依赖抽血），科室实时拥堵不同。系统**主动派下一站**。

算路算法（`RULE_EXAM.triageAlgorithm`）：

| 算法 | 逻辑 | 适用 |
|------|------|------|
| `FASTING_FIRST` | 优先空腹项 | 早高峰默认 |
| `LEAST_WAIT` | 选当前排队最少的科室 | 均衡负载 |
| `SHORTEST_PATH` | 当前等价 LEAST_WAIT（地理距离待补） | 预留 |
| `NONE` | 不自动派单 | 降级人工 |

硬性过滤：关联科室已挂起则绕开；前置 `depends_on_ids` 未完成则跳过。完成一项后事件驱动再算路。护士可 `forceRoute`、科室可 `suspendDept` 触发重路由。

## 3.5 场景对照

| 维度 | 门诊 | 药房 | 门诊医技 | 体检 |
|------|------|------|----------|------|
| 调度模型 | 线性单队列 | 池化分窗 | 并联独立队列 | 图路径规划 |
| 路径控制 | 系统 | 系统分窗 | 患者自主 | 系统主导 |
| 核心约束 | 顺序/优先 | 超时/窗口容量 | 报告时效 | 依赖/空腹/拥堵 |
| `source_type` | `CLINIC` | `PHARMACY` | `OUTPATIENT_EXAM` | `HEALTH_CHECKUP` |

# 4. 核心业务流程与状态机

## 4.1 排队单双状态

每条 `call_list` 同时有：

- **`state`（整数，叫号生命周期）** — 叫号器/大屏主用。
- **`triage_state`（字符串，分诊闸门）** — 签到、过号、配药、退号主用。

### state（叫号状态）

| 值 | 含义 | 何时写入 | 伴随动作 |
|----|------|----------|----------|
| 0 | 等候中（可被叫） | 入队且不需待签到；或签到完成后 | 进入叫号池 |
| 1 | 已呼叫 / 就诊中 | 医生呼叫、AutoCallNext | 写 `start_time`，可绑定诊室/医生 |
| 2 / 3 / 5 | （历史保留） | 当前流转**不写入、不读取** | 旧库若残留请勿当作业务态 |
| 4 | 就诊（或取药/采血）完成 | 医生点完成 | 写 `end_date` |
| 6 | 过号 | 医生过号或超时任务 | 可能重排或打入 PASSED |
| 7 | 待签到（未报到） | `requireSignIn=true` 入队 | 不进入叫号池 |

大屏按 `state=0` 显示等候，`state=1` 显示当前呼叫；过号展示还会结合 `triage_state=PASSED`。`2`/`3`/`5` 仅为历史保留值，现行引擎只使用 `0`/`1`/`4`/`6`/`7`。

### triage_state（分诊状态）

| 值 | 含义 |
|----|------|
| `UNARRIVED` | 已挂号未到院签到 |
| `WAITING` | 已签到，可叫号 |
| `REVISIT` | 复诊回流，可叫号且权重更高 |
| `PREPARING` | 药房配药中，不可叫号 |
| `PASSED` | 多次空呼后彻底过号 |
| `TESTING` | 去检查暂离（SuspendForTest） |
| `CANCELLED` | HIS 退号，护士同步作废 |

可被叫号的分诊状态通常为：`WAITING`、`REVISIT`，或空（兼容旧数据）。药房可叫号仅 `WAITING`。

## 4.2 门诊主路径

```
HIS/enqueue（可 requireSignIn）
    │
    ├─ 无需签到 → state=0, triage=WAITING
    └─ 需要签到 → state=7, triage=UNARRIVED
                    │
                    ▼ 自助机 / 护士代签到 / Triage/CheckIn
               state=0, triage=WAITING，写 check_in_time
                    │
                    ▼ 医生 AutoCallNext / 点名
               state=1，按各播报源开关播报（大屏/独立音响/门边屏），门边屏刷新
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
      完成(4)     过号(6)     去检查(TESTING)
         │          │
         │     次数 < maxSkipCount → 末位 WAITING
         │     次数 ≥ 上限 → PASSED
         ▼
      结束；复诊再入队 triage=REVISIT
```

预约号：携带 `appointmentStartTime` / `appointmentEndTime`。过早（早于开始超过约 30 分钟）拒绝签到；迟到超过结束宽限则把 `is_appointment` 从 1 降为 0，剥夺预约优先。

「过早约 30 分钟」与「迟到结束宽限」（当前代码为预约结束时刻后再加 30 分钟，见 `QueueServiceImpl.signIn` 的 `endTime.plusMinutes(30)`）均为**代码常量**，尚未纳入 `RULE_OUTPATIENT`。现场若需可调，应先扩展配置键（键名以代码为准），不要把这两个阈值写进规则中心现有 JSON 冒充已生效。

**时段穿插（R-3，叫号规则补全，设计项）：** 建议在 `RULE_OUTPATIENT` 增加 `appointmentSlotQuota`（每时段预约号/现场号配额，默认 6/4）与可配置阈值 `appointmentEarlyMin` / `appointmentLateGraceMin`（替换上述代码常量）；时段内按签到序，跨时段自动降级，与号源/预约体系联动（见差距分析附录 C R-3）。

**复诊回流入口（口径补齐）：** `triage_state=REVISIT`（当天已就诊再进队列，可叫且权重更高）的产生入口现状口径如下，落地字段以代码为准：① **HIS 再次挂号/入队请求带复诊标识**（推荐主路径，`EnqueueRequest.isRevisit`，设计项，见 §11.1）→ 直接以 `REVISIT` 入队；② 医生在叫号器完成时选择「复诊回流」（叫号器补操作键，设计项）；③ 护士站行内「标记复诊」（§16.3 补行内操作，设计项）。三者执行均写 `patient_flow_log` 事件 `REVISIT`（§4.6），门边屏/大屏按 `triage_state=REVISIT` 出「复」前缀（§18.3）。在任一入口落地前，复诊回流仅能由 HIS 再次挂号以**新普通单**进入（无复诊标记与权重）。

**入队幂等与一人多单（口径补齐）：** 门诊同科室同日同一患者仅保留一张可叫单——重复 `enqueue`（HIS 重复推送/重复扫码）应返回已有单或提示，建议幂等键 `(patient_code, dept_id, call_date, source_type)`；体检/医技患者天然跨多科室**并行多单**（一人多单不合并，由 `exam_record_detail` 逐项跟踪）；跨科室转诊后原科室单由 `ForceSwap` 关闭，不留双单。落地以代码为准，现状如无判重需在集成层或 HIS 侧先行去重。

## 4.3 药房路径

```
扫码 pharmacyCheckIn → 建单 PREPARING（通知配药）
        │
        ▼ pharmacyMarkReady（HIS Webhook 或药房台）

        │

```

## 4.4 检验采血路径

```
扫码 labCheckIn
  ├─ 已有本窗口 UNARRIVED → 核销为 WAITING
  └─ 否则新建 → 最短队列分窗 → WAITING
        │
        ▼ 窗口叫号 → 完成/过号
```

## 4.5 体检路径

```
套餐项目 exam_record_detail.state：
  0 未做 → 过滤挂起与依赖 → 算法选下一站 → enqueue 目标科，项目 state=1
  完成 → complete_time，项目 state=3 → 事件再算路
  科室 suspendDept → 踢出等待并重路由
  forceRoute → 护士指定下一站（可带预约特权）
```

**到科与离科衔接（口径补齐，不改变既有状态机）：** 患者被派往目标科室后如何进入该科叫号池，取决于体检入队是否 `requireSignIn`：

- `requireSignIn=false`（体检默认入队方式）：单直接进入目标科可叫池（`WAITING`），H5 显示“该项排队人数”即此态；患者未到科时被叫到，由叫号应答超时兜底（`callTimeoutMin` 过号 → 重排/计次，§4.2），不单独定义“到科登记”。
- `requireSignIn=true`（如需“人先到科、后叫号”）：单为 `7/UNARRIVED`，患者到目标科室在自助签到机（签到机须绑该科诊室，§19.3）或护士台代签（`ManualSignIn`）后才 `0/WAITING` 可叫。
- 科室间暂离（检查中/回诊）由 `SuspendForTest` / `ReturnFromTest` 收口，回流位置见 §11.2 口径。

## 4.8 加号与限号（设计项，F-2-9 / F-14-2）

**1. 场景与现状边界。「加号」** = 医生/护士/主任为患者**突破当日号源上限**（医生出诊 `doctor_schedule.max_quota` §9.7、时段配额 `appointmentSlotQuota` R-3）增加一号并进入排队，全过程**留痕可审计**。典型场景：复诊加号、老病人加号、院外转介、主任特批。现状边界（§1.3）：本系统**未实现**加号专用链路——`EmergencyOverride` 仅做队列内插队，`max_quota` 只登记不拦截；费用补收、号源池管理属 HIS 责任（本系统不收费）。本节为设计蓝图，落地以代码为准；未落地前加号走「HIS/人工放号 → 普通入队」。

**2. 加号入口与权限（设计项）：**

| 入口 | 终端 | 接口 | 说明 |
|------|------|------|------|
| 医生加号 | HJ叫号器（门诊模式） | `POST /DoctorCall/AddVisit`（A-4，§11.3） | 输入患者信息/就诊号 + 理由码，加号后按序入队 |
| 护士加号 | HJ护士工作站 | `POST /NurseDesk/AddVisit`（§11.8） | 护士台受理（电话/窗口/家属代办加号） |
| 主任一键加号/限号 | 管理后台主任台 | 规则快捷项（§14.3 模块⑥） | 科室/时段级批量放量或收紧 |

权限与防滥用：加号属**高危写操作**，服务端校验按钮权限码（建议 `add:grant` 加号、`add:limit` 限号，并入 §23.2 高危清单）；加号必须写原因码（建议：`REVISIT_ADD` 复诊加号 / `ELDER_ADD` 老人 / `VIP_ADD` 特需 / `OTHER_ADD` 其它）。建议在 `RULE_OUTPATIENT` 增加 `addVisitLimitPerDoctor`（每医生每半日加号上限，默认 5）与 `addVisitLimitPerDept`（科室每日上限，默认 20），达上限需主任授权（默认值落地以代码为准）。

**3. 号源与配额校验（设计项）：** 校验链 = 医生当日 `max_quota`（已约 + 加号）→ 时段配额 `appointmentSlotQuota`（R-3）→ 科室/医生加号上限 → 通过后入队；加号单沿用当日号段（`call_auto_num`，§9.13，跨日清零），不另起前缀，以 `add_flag` 区分；「一键限号」= 收紧配额/暂停该时段放号，写 `RULE_*` 覆盖并记 `sys_action_log`（`RULE_CHANGE`，R-9）。

**4. 数据与记录（设计项）：** `call_list` 增 `add_flag`（1=加号）/`add_reason`（理由/来源，C-14，见 §9.1）；新增 `add_visit` 加号记录表（T-16，见 §9.23），与 `call_list` 同生命周期（完成/退号后保留，供统计与纠纷取证）。

**5. 显示与统计（设计项）：** 大屏/门边屏是否对加号单加「加」标识由展示开关控制（**默认不显示**，避免患者间不必要信息）；主任台新增加号指标：加号数/加号率（当日加号 ÷ 号源）、按医生/科室排行、加号后爽约率（评估放号质量），数据口径对应 §14.3 模块③/⑥。

**6. 审计与 HIS 边界：** 加号动作写 `patient_flow_log`（`ADD_VISIT`）、`add_visit` 记录、配额/限号变更写 `sys_action_log`；号源池、预约、费用收补仍由 HIS 承担，本系统只做「放号 → 入队 → 叫号 → 统计 → 留痕」；如需 HIS 认可加号结果，经集成网关回传（§13，端点设计预留）。

## 4.9 业务日与跨零点处理（口径）

排队叫号需 24h 稳定运行（急诊、夜班、跨零点在途），业务日口径集中说明如下：

1. **默认业务日 = 自然日（00:00–24:00）**；如需医院业务日（如 06:00 日切、区分“昨天夜班”），以配置/代码为准（设计预留）。
2. `call_list.call_date` = 入队业务日（§9.1）。**跨零点在途单不因日切改变业务归属**：正在等候/就诊/过号的单继续流转，只在“当日队列 / 当日统计 / 归档”边界按业务日切分。
3. `call_auto_num` 跨日清零只作用于**取新号**（§9.13）：在途单的 `show_no`/`xh` 不因清零重置，不会出现“旧号被新号顶替”。
4. 归档（§9.2）与日报/看板统计按业务日；`call_date` 与真实时间戳（`create_time`/`check_in_time`/`start_time` 等）并存，排障时可互证。
5. 查询侧建议提供“业务日 + 日期时间”双口径入参（设计项，以代码为准），避免“今天 00:10 的单算昨天还是今天”的二义性。

# 5. 系统总体架构与技术栈

## 5.1 后端引擎 `pdjh-server`

- **形态：** 单模块 Maven Spring Boot 应用，包名 `com.gocent.pdjh`。
- **入口：** `PdjhServerApplication`。
- **分层：** `controller` → `service` / `service.impl` → `repository` → `entity`；另有 `integration`（HIS 网关）、`job`（超时过号等定时任务）、`dto`/`vo`、`config`（Security、CORS、WebSocket、启动种子）。
- **一致性：** 叫号改状态使用 Redisson 锁 `pdjh:lock:callList:{id}`，防止并发双呼。
- **持久化：** MySQL 8，`spring.jpa.hibernate.ddl-auto=update` 为开发建表来源；生产建议改为 `none` 并走手工 DDL。
- **缓存/锁：** Redis（Spring Data Redis + Redisson）。本地 `application.yml` 默认密码与 `docker-compose-infra.yml` 示例密码可能不一致，部署时用环境变量统一。
- **实时：** STOMP over WebSocket。浏览器端常用 SockJS；叫号器/音响用原生 `/api/pdjh-ws-native`。
- **监控：** Actuator 独立端口 9091，暴露 `health`、`info`、`prometheus`。
- **HIS 熔断：** Resilience4j 实例 `hisClient`。

## 5.2 前端矩阵

- **管理后台：** Vue 3 + Element Plus + Vuex，Hash 路由，登录后按角色菜单渲染。
- **显示类终端：** Vue 3 + Vite，Hash 路由（安卓路径更稳），共享 `@pdjh/common` 做设备绑定与姓名脱敏。
- **桌面端：** 叫号器 .NET 4.8 WPF；音响 .NET 8 WPF。
- **CI：** `.github/workflows/frontend-terminals.yml` 构建 screen / clinic / checkin / admin。**不含**护士站与体检 H5，这两端按第 24.2 节手动 `npm run build` 后分别部署到 `/nurse`、`/checkup`。

## 5.3 基础设施

仓库根 `docker-compose-infra.yml` **只起 MySQL 8 + Redis 7**，不起应用容器。

- MySQL：`pdjh` 库，`utf8mb4` / `utf8mb4_general_ci`，`lower_case_table_names=1`。
- Redis：AOF，compose 示例密码 `pdjh_redis_123`。

## 5.4 安全模型（当前实现）

- 业务接口大多 `permitAll`（`/Integration/**` 除外），鉴权依赖前端 Token 与业务校验，**不是**全接口 Spring Security 拦截。**分级鉴权**（IAM 补全，见 §23.2）：读接口维持现状；**高危写接口**（清队列、停诊、改规则、删用户、改权限等）在服务端按 `login_scene` + 按钮权限码校验，前端隐藏按钮不等于安全。
- 所有人员密码统一存 `users.pass_word`（BCrypt）；叫号器 `Doctor/Login` 校验 `users`，`doctor.password` 已废弃（见 §23.7/23.8）。`login_scene` 约束客户端：`ADMIN` 登管理后台、`NURSE` 登护士站、`DOCTOR/PHARMACY/LAB/EXAM` 登叫号器，跨端拒绝。
- 门边屏/大屏对患者姓名默认脱敏（`张*三`）。
- 监控口 9091 应只允许内网。

# 7. 统一约定：接口、鉴权、命名、脱敏

## 7.1 HTTP 约定

- 业务接口多数 **POST + JSON body**。少数列表/展示为 GET（如 `ClinicScreen/GetDisplay`、`Terminal/Resolve`、看板指标）。
- 完整 URL：`http://{host}:8081/api/{Controller}/{Action}`。
- 统一包装 `ResultData`：

| JSON 字段 | 类型 | 含义 |
|-----------|------|------|
| `success` | boolean | 是否业务成功 |
| `code` | int | 200 成功；400 参数；404 找不到；500 失败 |
| `msg` | string | 提示 |
| `data` | 任意 | 载荷 |

注意：HTTP 状态码经常仍是 200，业务失败看 `code`。前端 axios 拦截器可能对非 200 的 `code` 走 reject。

**业务错误码约定（建议值，以代码为准，P0-4）：** 保持四值语义（200 成功 / 400 参数 / 404 不存在 / 500 服务端）；如需细分供前端统一拦截与提示，建议按段位分配：`400xx` 参数与校验、`4040x` 目标不存在、`4090x` 业务状态冲突、`500xx` 服务端/第三方。`msg` 为可直接展示文案，同一业务失败全系统唯一措辞。典型失败映射建议：

| 失败场景 | 建议 code | msg 示例 |
|----------|-----------|----------|
| 缺参/参数非法 | `40001` | 参数缺失或非法 |
| 设备未注册 `NOT_REGISTERED` | `40401` | 设备未注册，请先绑定 |
| 目标（单/号/配置）不存在 | `40404` | 未找到对应排队单 |
| 无可叫等候（AutoCallNext 空队列） | `40405` | 当前无等候患者 |
| 终端待配置/冻结 `PENDING`/`FROZEN` | `40901` | 设备未启用，请联系护士台 |
| 终端类型不匹配（错壳） | `40902` | 终端类型不匹配 |
| 单已退号/已作废 `CANCELLED` | `40903` | 该号已退，请重新挂号 |
| 越权（无按钮权限/超出数据范围） | `40904` | 无操作权限 |
| 业务状态冲突（已叫号/已冻结/重复签到等） | `40905` | 当前状态不允许该操作 |

> 上表为**约定与建议值**，现状各接口具体 `code`/`msg` 以代码为准；前端拦截规则 = 非 200 → 弹 `msg`，`40904` 类可引导联系管理员。

部分实体为兼容旧 C# 客户端使用 `@JsonProperty` 大驼峰（如 `PatientCode`、`DeptID`、`ShowNo`）。新接口混用驼峰，调用方按各接口字段表传。

## 7.2 表命名

- 表名、列名：小写下划线（`call_list`、`dept_id`）。
- Java 字段驼峰，无 `@Column` 时由 Hibernate 转下划线。
- 历史坑：`is_forzen`（frozen 拼写保留）、`pass_word`、`deptID` Java 字段映射 `dept_id`。

已废弃：根目录 `mock_db_init.sql`、旧 `schema.sql`。测试数据用 `scripts/seed_pdjh_test_data.sql`。

## 7.3 设备编号

Android 壳 `getDeviceId()`：长度 ≤20，仅 `[A-Z0-9-]`，例如 `A3F9-K2M7-Q1WP-8X4C`。禁止 WiFi MAC、禁止超长 UUID 格式。H5 会截断非法值，但仍应以壳生成为准。

## 7.4 姓名脱敏

`packages/common` 的 `desensitizeName`：默认中间加 `*`。大屏 `SCREEN_CFG_*.nameDesensitize`、门边屏 `CLINIC_CFG_*.nameDesensitize` 控制是否开启。

## 9.13 `call_auto_num` 编号规则

| 列名 | JSON 别名 | 说明 |
|------|-----------|------|
| `gid` | GID | PK |
| `code` | Code | 规则编码 |
| `did` | DID | 关联科室或范围 |
| `name` | Name | 名称 |
| `auto_date` | AutoDate | 计数日期（跨日清零） |
| `type_a` / `type_b` / `type_c` | TypeA/B/C | 三类号段当前值 |

**号码生成与并发取号（口径，P0-1）：** `call_auto_num` 按 `did`（科室/范围）隔离号段，`code` 标识规则；TypeA/B/C 三类的业务语义由现场按 `code`+`did` 定义（如普通/专家/特需、或上午/下午/加号），当前值存 `type_a/b/c`。

- **跨日清零：** 取号时比较 `auto_date` 与业务日（§4.9）：不一致则先清零（`type_a/b/c` → 0、`auto_date` = 当日）再取号。清零只作用于“下次取新号”，**不影响在途单**（已发出的 `show_no`/`xh` 不重置）。
- **并发防重：** 取号/清零在 Redisson 锁内完成（建议键 `pdjh:lock:autonum:{code}:{did}`），避免并发取到同一号；失败重试以代码为准。
- **两套号码口径：** `show_no`（大屏展示号，如 A001，前缀由屏/科室规则拼装）与 `xh`（门边屏当日号序，如「初·09」中的 09 = 同科室当日序号）是不同口径，勿混用；`SyncAutoNum`（§11.9）用于与现场物理号机对齐。
- 加号单沿用当日号段、不另起前缀（§4.8 第 3 点）。以上细节（锁键、清零时机、前缀规则）落地以代码为准。

### RULE_MEDICAL_TECH

嵌套 `global`、`lab`、`ultrasound`、`radiology`、`ecg`。要点：

- global：`paymentSyncDelaySec` 缴费后开通取号延迟秒；`multiDeptMsgEnabled` 多科室提醒聚合；`noShowReleaseSlot` 预约未到释放时段（默认 true，R-14）。

- ultrasound：`roomCount` 4，预约开关与权重 7，分类型、空腹、急诊，各部位平均分钟。
- radiology：CT/MRI 台数，`ctSlotCapacity` 2，胸片是否预约，造影等待区 30 分钟，报告小时，危急值，急诊 CT 绿通。

### RULE_LAB

`interleaveRatio` 3，`missedPenalty` 3，`requireConfirmToFreeze` true，`tatWarningMin` 45（报告周转预警分钟）。

`RULE_LAB` 与 `RULE_MEDICAL_TECH.lab` 为**历史并存键**。规则中心「医技」页签的检验子页以聚合键 `RULE_MEDICAL_TECH.lab` 为准；`RULE_LAB` 仍可能被旧逻辑或导出快照读取。建议两键数值保持一致，避免检验窗口数、空腹优先等参数各读各的。

## 10.4 规则分层与参数归属（三层模型，设计项）

规则**按业务类型制定总规则**为主体，允许「院区 / 科室 / 诊室」特例覆盖（继承 + 覆盖）；**设备级只承载展示与播报配置，不承担调度规则**。禁止做成「每台设备 / 每个诊室一套完整规则」。

### 三层归属

| 层 | 内容 | 示例 |
|----|------|------|
| ① 业务类型总规则 | `RULE_*` 按业务场景（门诊 / 药房 / 医技 / 体检 / 通知）制定，医技按子类嵌套（§10.1） | 超时分钟、过号上限、重排位置、优先级权重、预呼叫、分流阈值、叫号间隔、窗口数、空腹截止、危急值 |
| ② 作用域覆盖 | 院区级（全局默认 + 院区覆盖，见差距分析附录 A）；科室 / 诊室级为可选三级扩展 | 某院区短信开关、体检算法；某诊区窗口数特例、某科室超时特例 |
| ③ 设备级（仅呈现） | 按屏配置，不参与调度 | `SCREEN_CFG` / `CLINIC_CFG` / `call_content` / `voice_channel`：语音文案、播报通道、音量、脱敏、模板路由 |

### 读取解析链

```
科室/诊室特例 → 院区覆盖 → 业务类型全局默认 → 代码内置默认
```

只读一份生效值，缓存键 `(ruleKey, scope)`（多院区见差距分析附录 A）。

### 判断标准

- 影响「谁先谁后、算不算过号」→ **调度规则**（① / ②）；
- 影响「怎么显示、怎么播」→ **设备级**（③）；
- 设备类型（`SCREEN` / `CLINIC` / `CHECKIN`）只决定终端形态，**不决定调度规则**。

### 特例治理

- 特例用「覆盖行」而非整份复制：只存差异键，读取时合并（数组字段整组替换）；
- 特例显式标记，规则中心「继承值打底 + 覆盖值高亮」（与附录 A 院区覆盖 UI 一致）；
- 特例设置写 `sys_action_log`（`RULE_CHANGE`）审计（R-9，§14.8）。

## 11.1 入队与签到 `/queue`

| 方法 | 路径 | 作用 | 入参 | 成功 data |
|------|------|------|------|-----------|
| POST | `/queue/enqueue` | 全院统一入队（HIS/第三方） | 见下表 EnqueueRequest；**`deptID`、`patientName` 必填**；**门诊普通号**另必填 `officeRoomId`（体检/医技入队不强制） | CallList |
| POST | `/queue/signIn` | 按患者号签到 | `patientCode` | true |
| POST | `/queue/getSignInInfo` | 签到前预览（校验设备覆盖诊室） | `patientCode`，`deviceCode` 或 `deviceId` | 匹配的待签到 CallList |
| POST | `/queue/pharmacyCheckIn` | 药房扫码建单+分窗 | `patientCode`，`deviceCode` | 含窗口信息的结果 |
| POST | `/queue/pharmacyMarkReady` | 配药完成 PREPARING→WAITING | `callListId` | CallList |
| POST | `/queue/labCheckIn` | 检验扫码分窗直接 WAITING | 同药房签到 | 结果 |
| POST | `/queue/pharmacyDeskQueue` | 药房台列表 | `officeRoomId` | PREPARING+WAITING 列表 |

**EnqueueRequest 字段：** `patientCode`，`patientName`（必填），`sex`，`ageStr`，`deptID`（必填），`officeRoomId`（**门诊普通号**必须指定物理诊室；体检/医技入队不强制），`queueType`（挂号/取药/抽血说明），`showNo`，`priority`，`doctors`，`doctorID`，`requireSignIn`（true→待签到 state=7），`isAppointment`，`appointmentStartTime`，`appointmentEndTime`，`sourceType`，`isRevisit`（复诊回流标记，设计项，见 §4.2）。

**入参落库口径：** `priority` 为兼容入参，**不直接落 `call_list` 列**——优先级由排序权重模型/插队改写 `priority_weight` 承载（R-1 设计项，§9.1）；`queueType`（挂号/取药/抽血说明）仅业务说明**不入库**，如需留痕写入 `remark`/`doctors`。落地以代码为准。

失败：缺参 400；签到找不到 404。

**入队口径（幂等与一人多单，C-7）：** 门诊同科室同日同一患者仅保留一张可叫单，重复 `enqueue`（HIS 重复推送/重复扫码）返回已有单或提示，建议幂等键 `(patient_code, dept_id, call_date, source_type)`；体检/医技患者允许跨多科室并行多单（一人多单不合并，由 `exam_record_detail` 逐项跟踪）；转诊后原科室单由 `ForceSwap` 关闭，不留双单。落地以代码为准（详见 §4.2）。

## 11.2 分诊引擎 `/Triage`

| 路径 | 作用 |
|------|------|
| POST `/Triage/CheckIn` | 二次签到 UNARRIVED→WAITING。**旧客户端兼容入口**，与 `/queue/signIn` 效果一致（都把未报到单放进可叫号池）；新签到机、H5 请走 `/queue/signIn` |

# 13. HIS / LIS / PACS 集成网关

现场按院情选一种主模式，可与 Webhook 并存。

**LIS / PACS 回推：** 检验科（LIS）采血完成、放射/超声等检查系统（PACS/RIS）检查完成时，由对方调用 `/integration/webhook/exam/status` 推送进度。排队系统据此把对应体检/医技子项标为完结并触发下一站算路。HIS 负责挂号入队；LIS/PACS 负责「这项已经做完」。报文里的 `state=4` 是对方完成标志，写入本地 `exam_record_detail.state=3` 须经集成层转换（见 11.16）。

## 13.1 主动 HTTP

排队当消费者，定时或事件触发调院方 REST/SOAP。适合有集成平台的医院。配置连接 `type=HTTP`、`base_url`、鉴权账号，在端点上配 path/method，映射规则把 JSONPath 指到 `patientCode`、`deptID` 等入队字段。优点：节拍自主、好重试；缺点：依赖对方时延。

## 13.2 被动 Webhook

排队当服务方。LIS/PACS 在检验或检查完成时推送 `patientCode`、`itemCode` 及对方状态码（完成常用 `state=4`），经转换后触发体检下一项。须 IP 白名单。挂号也可推 `/his/register` 直接入队。

## 13.3 JDBC 轮询

只读账号 + 视图，禁止写 HIS。端点 `method=POLLING` + cron，增量游标扫当日挂号。适合无接口的老 HIS。缺点：表结构变更会断、对库有只读压力。

## 13.4 边缘探针

院方禁止入站时，在边界机部署单向出站 Agent，读内网视图后推到排队 Webhook。核心服务不必对 HIS 网段开入站。

## 13.5 实施工具

后台「数据源接口配置」维护连接与映射；「运维护航沙盘」看成功率与耗时；Dry-Run 注入样例 JSON 看映射结果；配置历史可 rollback；Marketplace 导入卫宁/东软等模板。Mock HIS 在无对方环境时跑通签到-叫号-大屏。

决策顺序：有总线 → HTTP；有事件广播 → Webhook；只能读库 → JDBC；不能入站 → Edge Agent。

## 14.3 主任工作台

五个业务线看板 + 全院统计，给科主任日常盯盘，不是给 IT 配设备。

| ⑥ 规则自治 | 一键加号/限号（机制与边界见 §4.8，设计项）、停诊/恢复、配额调整、体检算法切换；变更审计回溯 | 【已有】体检一键切、规则快捷项；其余补强 |
| ⑦ 通知与通告 | 停诊改签批量短信/微信；科室公告下发到屏；批量催报到/催取药 | 补强 |
| ⑧ 报表与导出 | 日报/周报/月报自动生成 + 定时推送；Excel 导出；多院区对比 | 补强 |

**分级权限：** 科主任看本科室（`data_scope=2`）、院区主任看本院区（`data_scope=4`）、院长/医务看全院（`data_scope=5`，§23.5）；每个模块按数据范围过滤，多院区叠加 `campus_scope`（见差距分析附录 A §A.8）。

**三期路线：** 一期 = 模块①②③ 指标补强（现有 dashboard 数据即可）+ ④ 超时预警一键处置；二期 = 停诊批量 + 改签通知、规则自治 + 审计、设备在线监控；三期 = 预测等候、同比环比、自动报表、多院区对比。

**1. 入口与权限**

**4. 保存与生效**
- 点「保存」：先做**本地校验**（必填、边界、JSON 结构、模板占位符），通过后调用 `SaveConfig` 写入 `sys_config`；校验失败字段级红字提示、不提交。
- 生效机制：调度引擎按周期扫描读取，**一般不必重启后端**；缓存按 `(ruleKey, scope)` 失效（多院区设计项，见差距分析附录 A）。
- 保存即审计：写 `sys_action_log`（`log_type=RULE_CHANGE`，`payload` 含改前/改后 JSON 与操作人）。变更历史入口在规则中心顶部「变更历史」。

**5. 恢复默认 / 快照**
- 恢复默认：一键恢复内置默认 JSON（二次确认，§14.13 UI 原则）；已设院区覆盖时仅恢复当前作用域。
- 导出快照：下载当前作用域全部规则 JSON（含时间戳）。
- 导入快照：上传 → 预检（schema 校验）→ 确认 → 覆盖当前作用域；导入同样写审计。

**6. 作用域选择器（设计项，多院区，见差距分析附录 A）**
- 选「全院」：编辑 `RULE_*` 全局默认行（等于现在的行为）。
- 选某院区：展示**继承结果**——全局值打底、院区覆盖字段高亮；提供「编辑覆盖」（只存差异键）与「恢复默认」（删除覆盖行回退继承）。
- 科室级特例为可选三级扩展，v1 不提供。

**7. 变更历史（R-9）**
- 点「变更历史」：按规则键 / 时间范围检索（操作人、时间、改前/改后 diff）；用于规则调整回溯与纠纷排查。

**8. 注意事项**
- 不要在「全局字典参数」（§14.11）里把 `RULE_*` 改成非法 JSON（只读查看）。
- 数字字段的单位（分钟/次数/人数）与边界均标注在输入框旁；修改后建议到对应主任台（§14.3）观察指标变化验证效果。

## 14.14 屏幕预览（设计项）

**目标：** 后台可「同步查看某块屏幕的显示情况」，用于配置确认与排障；**只读模拟渲染，零影响现场运行**。

**1. 核心原则**
- 预览 = 用同一套「模板组件 + 该屏配置（`SCREEN_CFG`/`CLINIC_CFG`/`CHECKIN_CFG`）+ 关联范围队列数据」再渲染一份画面，所见即现场所显；
- 全程只读：不写库、不发叫号指令、不触发播报、不改设备状态。

**2. 入口与形态**
- 「屏幕管理 / 候诊区大屏配置 / 门边屏显示配置」均加「预览」按钮（列表行 + 编辑页）；
- 各模板工程提供**预览路由**（如 `/screen/#/preview?deviceCode=xxx&preview=true`），管理后台 iframe 打开，可多屏并排（tab / 抽屉）对比；
- 预览 URL 短时效 + 登录态校验，避免裸 URL 泄露屏幕内容。

**3. 数据与同步（三档，推荐 A + B）**

| 档 | 做法 | 同步度 |
|----|------|--------|
| A 定时快照 | 拉一次配置 + 队列渲染，10s 轮询刷新 | 秒级延迟 |
| B 实时订阅（推荐） | A + 订阅 `/topic/hall`（过滤该屏范围），叫号事件即刷新 | 准实时 |
| C 截图/推流回传 | 现场屏截图或录屏回传后台 | 像素级（成本高，不推荐） |

**4. `preview=true` 标记与旁路清单（零影响的关键）**

| 干扰源 | 防范 |
|--------|------|
| 心跳误判 | 预览请求带 `preview=true` → 后端**不写 `last_seen_at`**，避免屏"在线"误判 |
| 误触发播报 | 预览**不订阅 `/topic/voice`、不调 `DocCallMsg`**——不触发音响/本机 TTS |
| 设备状态污染 | 预览**不调用** `Register`/`Resolve`（设备注册流程）；走独立只读预览接口或现有接口加 preview 参数旁路副作用 |
| 数据一致性 | 预览与现场读**同一份**配置与队列数据源；预览为只读快照，标注「可能与现场存在秒级延迟」 |

**5. 使用场景**
- 改完 `SCREEN_CFG`/`CLINIC_CFG` 先预览确认，再保存生效（§14.5/§14.6）；
- 屏显示异常时「预览 vs 现场」对比排障；
- 多屏/多角色并排预览（§2.5 屏幕角色、§2.6 样式模板）；
- 验收演示。

# 15. HJ叫号器 — 功能与使用说明

Windows 桌面客户端，产品名 **HJ叫号器**，解决方案 `HJ叫号器/Gocent.CallStation.sln`，.NET 4.8。门诊诊室、药房窗口、检验窗口、医技/体检检查室共用同一套程序。内部工程名为 `Gocent.CallStation`（由历史工程名 `Gocent.DoctorStation` 更名，.sln/.csproj 同步）。`App.config` 配置 `ApiBaseUrl`（如 `http://服务器:8081/api`）和 `WsUrl`（`.../pdjh-ws-native`）。

登录后后端按科室 `businessType` 返回 `stationMode`：`CLINIC` 门诊、`PHARMACY` 药房、`LAB` 检验、`EXAM` 医技/体检。界面操作键统一为：呼叫下一位、重呼、过号、完成、点名呼叫；点位名词在「诊室 / 窗口 / 检查室」间切换，窗口/诊室切换与退出见 15.4。

## 15.1 登录窗（约 360×300）

- 显示医院名称与「HJ叫号器」。
- 工号或手机号 + 密码（可显隐）。
- 「忘记密码」调用 `Doctor/RequestPasswordReset`，等待管理员重置。
- 默认密码 123456；`must_change_password=1` 时弹出是否立即改密（`ChangePassword`）。
- 登录接口 `POST /Doctor/Login`。药房账号与门诊账号走同一客户端，不再分流到另一套安装包。

## 15.2 列表版（约 300×800）

适合固定工位竖屏。门诊、检验、医技体检使用此窗。

**展示：** 当前呼叫（号码、脱敏或全名按院规，可含性别/年龄/初复诊/预约类型摘要，ST-5）、WebSocket 在线灯、等候 / 已完成 / 过号三个列表、当日个人统计（叫号/完成/过号/点名量，ST-12）。

**队列辅助（ST-1/ST-2）：** 当前单显示 `callTimeoutMin` 剩余倒计时与剩余重呼次数（`callRepeatCount`）；等候列表显示「前面还有 N 人」与预计等候分钟（F-5-7），并对优先/插队/复诊/特殊人群（`priority_weight` / `special_flag`）加标识。

**双医同室（ST-3）：** 同室两名医生时，列表按 `doctorId` 只显示自己的队列（`GetDocCallList` 带 doctorId 过滤，§11.3），两侧互不干扰。

**锁定患者显示（设计项，§16.6）：**
- 等候/当前列表中，**锁定给当前医生的单显示「锁」高亮标记**（`locked_doctor_id` = 本人），点名呼叫时一眼可辨；
- **锁定给他人的单不在其他医生的列表中出现**——服务端过滤，医生端只展示「本人可叫」的单（§16.6 叫号过滤规则）；
- 共享队列（`doctor_id` 为空）模式下，本医生列表 = 共享池 − 锁给他人的单 + 锁给自己的单（高亮「锁」）；独立队列（双医同室）模式按 `doctorId` 隔离，锁标记同样展示。

**操作：**

| 按钮 | 行为 |
|------|------|
| 呼叫下一位 | 取等候队首呼叫，带当前 `deptId`+`officeRoomId`+`doctorId` |
| 重呼 | 对当前单再发 `DocCallMsg`，大屏音响再播 |
| 过号 | `EditCallMsgState` state=6 |
| 完成 | state=4 |
| 点名呼叫 | 从等候列表点选某人呼叫（不是队首） |
| 切换窗口/诊室 | 打开 `RoomSelectWindow` 重新上岗 `BindSittingRoom`，见 15.4 |
| 暂停/恢复叫号 | `PauseCall`/`ResumeCall`（R-7）：暂停后 `AutoCallNext` 拒绝并提示，用于医生离岗/接诊特殊患者（ST-4） |

**快捷键（ST-6，设计项）：** F1 呼叫下一位、F2 完成、F3 重呼；「自动叫号」开关可选（完成当前后自动呼叫下一位，需确认防误）。

药房模式走 `PharmacyDeskWindow`：在上述叫号能力上增加「配药中」列表、配药完成兜底、扫码叫号。检验窗口同样用叫号接口，流程日志记 LAB_* 事件。药房模式同样提供悬浮窗（ST-9，见 15.3）。

## 15.3 精简悬浮窗

可拖拽圆形置顶，不抢 HIS 焦点。悬停展开：完成、呼叫下一位、重呼、过号、切换、退出。高频动作与列表版同一套 API。药房模式同样提供悬浮窗（ST-9，设计项）；当前若未实现，药房窗口先用列表版。

## 15.4 窗口选择 / 改密 / 退出

`RoomSelectWindow` 列出本科室开放诊室或窗口，确认上岗（`BindSittingRoom`）。`ChangePasswordWindow` 改密。退出有确认（`LeaveSittingRoom`），避免误关导致不叫号。

**换班交接（ST-7，设计项）：** 下班前执行「交接」：提示处理当前单（完成 / 过号 / 转交）、确认未完成队列归属；当日统计按 `doctor_id` 归属不变；交接动作写 `patient_flow_log` / `sys_action_log` 留痕。

## 15.5 使用注意

- 必须先在后台排班或绑定窗口，否则门边屏没有值班信息。
- 叫号粒度带上 `officeRoomId`，才能与门口屏一致，避免一科多室串屏。
- 一台叫号器同一时间只绑一间诊室/窗口。
- 在线灯灭时仍可能用 HTTP 叫号，但大屏刷新会变慢，应检查 WS 与 Nginx Upgrade。
- **离岗保护（ST-8，设计项）：** 无操作超时（默认 10 分钟）自动暂停叫号并锁屏，需重新登录/确认；避免医生离岗后 `AutoCallNext` 空转。
- **误操作保护（ST-10，设计项）：** 完成/过号为高危操作，可配置二次确认；可选「撤销最近一次操作」（如误完成 → 回到就诊中，需权限与审计）。
- **医生端复活（ST-11，设计项）：** 过号列表行内提供「复活」（调 `TriageAdmin/Revive` 或医生侧接口，原因码可选），不必离座找护士。

# 16. HJ护士工作站 — 功能与使用说明

Web：`HJ护士工作站`，开发 `http://127.0.0.1:5175`，部署 `/nurse`。登录后 `GetSession` 限定**会话诊区**（当班诊区，见 §16.1）。

**定位：告警驱动、签到兜底、队列干预；不代叫号。**

## 16.1 登录与当班诊区

使用 `users` 中 `login_scene=NURSE` 的账号。token 之后每个 NurseDesk 请求都带。

**当班诊区（与医生「坐诊诊室」对称）：** 护士可能今天在内科诊区、明天在外科诊区，`users.dept_id` 仅为**常驻科室/诊区**，不固定会话范围。登录时确定「会话诊区」，优先级：

1. **当日排班**：查 `nurse_schedule`（user_no + date）取当班诊区（推荐主路径，后台「护士当班排班」维护）；
2. **登录选择**：无排班时登录页下拉选择当班诊区（仅列出其授权诊区，兜底）；选择后落成当日 `FULL` 排班；
3. **常驻回退**：都无则回退 `users.dept_id` 常驻诊区，并提示「今日无排班，按常驻诊区」。

**规则：**
- 可选的诊区 = **授权集合**。v1（未接 `data_scope`/`campus_scope`）= 常驻诊区及其同父兄弟诊区节点 + 该护士历史排班诊区，不能任选全院叶子科室；
- 当班中途支援其它诊区可「**切换诊区**」（`/NurseDesk/SwitchZone`，须授权，写 `nurse_action_log` `SWITCH_ZONE`，并覆盖今日排班）；
- `GetSession`（§11.8）返回会话诊区、科室、诊室列表，范围以**会话诊区**为准；护士操作日志 `zone_id` 用会话诊区；
- 与 §23.5 数据权限一致：会话诊区决定所有列表/干预接口的行级范围。

## 16.2 工作台内页面

| 页面 | 文件 | 做什么 |
|------|------|--------|
| 总览 | DashboardPage | 候诊人数、未签到、过号、告警条 |
| 操作区 | OperationPage | 扫码/手输就诊号代签到；搜患者；插队、复活、转诊、冻结 |
| 呼叫协助 | CallAssistPage | 协助医生侧状态查看（不替代叫号器顺呼） |
| 诊室与设备 | RoomsDevicesPage | 诊室开放、换房 `MigrateRoom` |

## 16.3 操作区详细用法

1. 扫码枪焦点在输入框，扫就诊号回车，或手工输入点「确认签到」→ `ManualSignIn`。可勾选免二次扫码原因 `NO_SECOND_SCAN`。
2. 搜索姓名/就诊号，按状态（候诊/过号/已就诊）和诊室筛选。
3. 行内操作：代签到、补绑诊室、过号复活、插队、转诊、冻结、**标记复诊**（设计项，见 §4.2）、**锁定医生/解锁**（共享队列预指定接诊医生，见 16.6）。每次要选原因码并建议填备注，写入 `nurse_action_log` 与患者流程日志。
4. HIS 已退号：`MarkHisRefunded`，队列变 CANCELLED，避免继续叫到已退患者。

**干预口径（业务闭环补充，C-6/C-10）：**

- **复活会计：** `Revive` **不重置 `call_count`**，复活后按 `requeuePosition` 重排（§10.1）；同日同一单反复复活受**频控上限**约束（建议默认 3 次/日，超出需二次确认 + 备注，防绕过 `maxSkipCount`/PASSED 上限；默认值以代码为准）。复活事件 `NURSE_REVIVE` 全量留痕（§4.6）。
- **退号时序：** `MarkHisRefunded` 只对**未叫号（state=0/7）与已过号（6）**单同步作废；`state=1` 就诊中/已叫号未到的单应**先完成或过号收口**，再由 HIS 退号、护士作废——避免进行中单据被撤销造成“就诊中单消失”、统计与流程日志断链。

## 16.4 换房

`fromRoomId` → `toRoomId`，可选是否把医生一起迁。用于诊室检修。失败 400 会返回原因（目标关闭、无权限等）。

## 16.5 停诊

`SuspendDept` 挂起科室：体检会重路由；门诊应配合医生停诊，避免继续入队。恢复用 `ResumeDept`。

**停诊后“在途患者”处置链（口径补齐，C-2）：** 停诊/挂起只阻止**新单入队**，已在队列中的单需现场处置闭环，动作任选其一并留痕（`nurse_action_log` + 必要通知）：

1. **在途可叫单（已签到 WAITING/候诊）**：转诊到同诊区可接诊医生/诊室（`ForceSwap`，§11.8）或当面退号（`MarkHisRefunded`）；无法即时处置的由护士在操作区逐单处理，**不得停诊后留在队中被继续叫到**；
2. **已约未到单（UNARRIVED/预约）**：改签他日或退号，并触发通知（短信/微信，通知域默认关闭时由护士/前台人工电话告知，§10.1 RULE_NOTIFICATION）；
3. 停诊时长内仍被叫到的兜底：`SuspendDept` 后目标科室队列对 `AutoCallNext` 应拒绝/提示（口径，落地以代码为准）；
4. 停诊批量 + 已约改签通知为主任台补强项（§14.3 模块④，设计项，F-14-5/F-2-7）。

## 16.6 患者-医生锁定（共享队列，设计项）

- **场景：** 多医生共享科室队列（`doctor_id` 为空、谁叫归谁）时，护士把点诊/有特殊需求的患者**直接锁定给某医生**，只能由该医生叫号就诊。
- **与队列形态的关系：** 独立队列（入队即定医生，双医同室，§15.2）与共享队列（`doctor_id` 为空）两种形态并存；**锁定是共享队列的预指定特例**（写 `locked_doctor_id`，字段见 §9.1）。
- **叫号过滤规则：** 医生 A 取队列（`GetDocCallList` / `AutoCallNext`）只取「`doctor_id` 为空 且（`locked_doctor_id` 为空 或 = A）」的单；锁给其它医生的单对 A **不可见不可叫**；被锁定医生可顺呼或点名。医生端展示见 §15.2「锁定患者显示」——锁给本人的单高亮「锁」标记，锁给他人的单不在列表出现。
- **操作与审计：** 护士行内「锁定医生」（选医生 + 原因码，`/NurseDesk/LockDoctor`，§11.8），写 `nurse_action_log`（`LOCK_DOCTOR`）与 `patient_flow_log`（`NURSE_LOCK_DOCTOR`）；解锁 `/UnlockDoctor`（`NURSE_UNLOCK_DOCTOR`）。
- **流转边界：** 锁定**不改排队顺序**（仍按序/权重），只限定"谁能叫"；完成/过号自动解除；转诊（ForceSwap）清除锁定；**锁定 ≠ 叫号**（护士不代医生呼叫，符合 §2.4 边界）。
- **与其它干预兼容：** 插队、冻结、复活、补绑诊室等与锁定可叠加，互不冲突。

# 17. HJ候诊区大屏 — 功能与使用说明

横屏、常亮、Kiosk。服务根不要带 `/screen`。改配置保存后台即可，刷新大屏或等下次拉取。

# 18. HJ诊室门边屏终端 — 功能与使用说明

目录 `HJ诊室门边屏终端`，9:16 竖屏，base `/clinic/`。开发 5175。Hash 路由 `/` 主屏、`/bind` 绑定。守卫：未 READY 不能进主屏。

## 18.1 产品目标

让患者在门口确认「这间房是哪位医生、现在看谁、后面还有谁」，减少进错诊室。**不发起叫号**（无叫号按钮、不抢叫号权）、不签到、不做触摸配置；可选**本地语音播报**叫号内容（见 §18.6）。

## 18.2 绑定

与大屏相同的双线：Register 待配置 / 手工 deviceCode。`terminalType=CLINIC`。Resolve 成功后固定进入 `/clinic/` 站点，并按返回的模板路由渲染样式（默认 `/clinic-default`，设计项 §2.6——模板只改样式，单/双医内容布局与一屏一室绑定不变）。若解析到 SCREEN 设备，绑定页提示装错壳。

后台：屏幕类型 CLINIC → 关联恰好一间诊室 → 启用 → 配 CLINIC_CFG。

## 18.3 主屏布局

数据 `GET /ClinicScreen/GetDisplay?deviceCode=`。

- **顶栏：** 医院名、Logo、诊室名、楼层房号、公告。
- **医生区：** 1 名医生用单栏（头像、姓名、职称、专长、简介）；2 名医生用双栏——**左栏医生 A、右栏医生 B，各自独立显示「当前叫号 + 等候列表」**（按 `doctorId` 分组，数据来自 `GetDisplay` 的 `doctors[]` / `currentPatients[]` / `waitingPatients[]`，见 §11.9）。无人坐诊显示待机/占位。
- **当前就诊：** 按医生区分，号码 + 脱敏姓名。初复诊前缀：`triageState=REVISIT` 显示「复」，其余显示「初」。示例：初诊 `初·09·张*花`，复诊 `复·05·李*明`。
- **等候列表：** `showWaitList=true` 时滚动等候；间隔 `scrollIntervalSec`。双医时按医生分栏各自滚动，两侧互不影响。
- **底栏：** 提示语。
- 屏幕冻结、未绑诊室、未注册：`StandbyView` 中文原因，不白屏。

## 18.4 刷新

大厅 `STATE_UPDATE` 后重新 GetDisplay；无 WS 则按滚动间隔轮询。医生 `BindSittingRoom` 后下一轮即显示新医生。

## 18.5 非功能

硬件可选部署，但软件能力必须可验收。无触摸业务键。隐私：默认脱敏。

## 18.6 本地叫号播报（本地 TTS，可选，新增）

- **能力：** 门边屏作为**播报终端**，收到叫号事件（`/topic/hall` 的 `STATE_UPDATE`）后可**本地 TTS 合成播报**当前叫号，适合独立音响未覆盖的诊室（分散诊区、独立检查室等）。
- **开关：** `CLINIC_CFG_{id}.voiceEnabled`（默认 false，见 §10.2）。关闭时门边屏只显示不发声。
- **文案：** 默认复用 `doc_screen.call_content`（占位 `{0}` 号序 `{1}` 姓名 `{2}` 诊室，可选 `{3}` 医生名）；可在 `CLINIC_CFG_{id}.voiceTemplate` 单独配置，未配置时回退 `call_content`。双医同室时建议启用医生名占位，患者可区分是哪位医生叫号。
- **触发机制：** 门边屏收到 `STATE_UPDATE` 后刷新 `GetDisplay`；若 `voiceEnabled=true` 且当前存在 `state=1` 叫号，则本地合成播放（音量 `voiceVolume` 默认 80、音色 `voiceLang` 默认 `zh-CN-female`，同大屏约定）。
- **独立性（不再互斥）：** 各播报源——独立音响 / 候诊大屏本机 / 门边屏本机——**各自独立开关、互不影响**。同一叫号可能同时由音响与门边屏播出，由现场按区域覆盖决定开启哪些源；独立音响已覆盖的区域可关闭门边屏本地开关，避免重复播报（操作建议，非强制机制）。
- **硬件要求：** 门边屏主机需自带喇叭或外接小音箱；音量接入 `voiceVolume`。

# 20. HJ音响终端 — 功能与使用说明

.NET 8 WPF，托盘常驻，`System.Speech` 中文 TTS。不是网页。

## 20.1 安装

`dotnet publish` 自包含单文件到现场工控机，接功放。首次打开设置窗：后端根地址 `http://服务器:8081`、设备编号（与后台音响台账一致）、开机自启。

## 20.2 工作原理

连接 `pdjh-ws-native`，订阅 `/topic/voice/{设备编号}`。播报句子 = 触发叫号的那块候诊大屏的 `doc_screen.call_content` 填入号、姓名、诊室（占位 `{0}` `{1}` `{2}`，可选 `{3}` 医生名，双医同室区分医生），与大屏本机 TTS 的 `SCREEN_CFG.voiceTemplate` 无关。**叫号范围 = 该音响覆盖的诊室集合**：经 `voice_scope_mapping` 绑定大屏（大屏再关联诊室）后覆盖其诊室范围，也可直接绑定诊室（`scope_type=OFFICE_ROOM`，可选）；覆盖范围内的叫号直接播报。一台音响可被多块大屏勾选。

## 20.3 现场步骤

1. 后台独立音响管理新增编号。
2. 屏幕管理（SCREEN）配 **`call_content` 音响文案**、关联诊室、绑定该音响，通道选独立音响（大屏本机 TTS 模板仍在「候诊区大屏配置」的 `voiceTemplate`）。
3. 程序保存并连接，托盘「测试播报」。
4. 故障：该大屏通道改为「大屏播报」。

关闭设置窗不会退出；退出需托盘菜单。`play_mode=HTTP` 时后端向 `endpoint_url` POST 文本，给第三方音箱网关。

## 20.4 播放队列与防打断（多诊室并发叫号，新增）

- **场景：** 一台音响绑定多个诊室（多块大屏或直接绑诊室，见 20.2）。同一时刻多个诊室几乎同时叫号时，多个播报文本会先后到达 `/topic/voice/{设备编号}`。
- **行为要求（硬性）：** 音响终端维护**播放队列（FIFO）**，按到达顺序逐条播报；**新到达的叫号文本不得打断正在播报的内容**，一律追加到队尾，按顺序播完后再播下一条。
- **去重（建议）：** 同一 `callListId` 的重复推送（重呼、重复事件）在队列中只保留一条：已入队未播则替换为新文本，正在播报则忽略重复，避免同一患者被连续播两遍。
- **优先级插队（可选扩展，默认不启用）：** 急诊/绿色通道等紧急叫号如需抢先播报，由后端在推送消息中携带优先级字段，终端仅在空闲或队首未播时按优先级调整；默认策略严格遵守「不打断当前播报」。
- **实现建议：** 排队在终端本地完成（.NET 端 `Queue<播报文本>` + 单播线程），简单可靠、不依赖后端；如后续需要服务端统一排序、去重统计或「播报完成回执」，可增加回执接口（设计预留，实现以代码为准）。
- **HTTP 模式：** `play_mode=HTTP` 推第三方音箱网关时，由后端按 `deviceCode` 维护发送队列**串行 POST**，同样不打断、不并发推送（网关侧播放行为由第三方实现）。

# 23. 权限、角色、登录

## 23.1 配置顺序

1. 菜单管理维护 `sys_menu`（启动 `SysMenuSeedRunner` 会写最小树）。
2. 角色勾选菜单，`CommitPermission` 写 `sys_role_menu`；需要时勾选**按钮权限**（`sys_button_permission`）。
3. 用户必须选角色（可多角色，写 `users_roles`）；`users.role_id` 关联主角色，`users.role` 同步 `role_code`。
4. 设置数据权限：`users.data_scope`（1 本人 / 2 本科室 / 3 本诊区 / 4 本院区 / 5 全院）+ `campus_scope`（多院区，见 §23.5）。
5. 登录 `User/LoginUser` 按授权组装前端路由（菜单并集 + 按钮权限码）。
6. 高危写接口由服务端按 `login_scene` + 按钮权限码二次校验（见 §23.2）。

`AdminBootstrapRunner`（Order 101）：若无系统管理员则创建 `ROLE_ADMIN` 并授权全部未禁用菜单（含按钮权限全量）；若无 `wuaitecadmin` 则创建超管（密码 BCrypt，明文常量在代码 `ADMIN_DEFAULT_PASSWORD`，不写进 SQL）；已有超管缺 role_id 则补绑；启动时升级遗留明文密码。

叫号器走 `Doctor/Login`（内部校验 `users` + `login_scene` 为叫号器岗位）。护士站走 `User/LoginUser` + `NURSE`；管理后台走 `User/LoginUser` + `ADMIN`。

> **注：** 本章按对标三甲 IAM 分析（《对标三甲医院叫号系统差距分析》附录 B，IAM-1～IAM-11）补齐设计；标注「IAM 补全」的字段/表/接口为设计项，落地以代码为准。

## 23.2 API 层与接口鉴权

- **现状基线：** 除集成部分外业务 API 未做全局部署级网关鉴权，读接口维持 `permitAll` + 前端路由权限；生产应限制管理网段、关闭公网 8081/9091。
- **分级鉴权（IAM-1）：** 读接口维持现状；**高危写接口**在服务端校验，顺序为：登录态（token）→ `login_scene` 白名单 → 按钮权限码（`sys_button_permission`）→ 数据范围校验。
- **高危写接口清单（建议，随版本维护）：** `OneclickClear`（清队列，仅 ADMIN）、`SaveConfig`/`DeleteConfig`（规则/配置，仅 ADMIN/授权角色）、`RemoveUser`/`CommitPermission`/`SaveButtons`（用户与权限，仅 ADMIN）、`SuspendDept`/`SuspendDuty`（停诊，本科室管理员/护士长）、`EditorCall`/`SortCall`（改号/调序，本科室）、`AdminResetPassword`（仅 ADMIN）。缺省策略：**写操作默认拒绝，显式放行**。
- 前端「隐藏按钮」不等于安全，所有敏感操作必须走后端校验。

## 23.3 密码与账号策略（IAM-5 / IAM-7）

- 新建用户默认 `123456` 且 `must_change_password=1`（既有约定，§9.14）；`PWD_POLICY` 可配置复杂度、有效期、失败锁定与历史密码防重用（默认值见 §10.3）。
- 连续登录失败达 `PWD_POLICY.failLockCount` 次锁定账号 `lockMinutes` 分钟，写入 `login_log`；解锁由管理员处理或到期自动解锁。
- 账号生命周期：批量导入（`/User/BatchImport`：模板下载 → 预检 → 确认，密码默认 `123456` + 强制改密或随机初始密码，操作细节见 §14.11）、离职一键禁用（`/User/Disable`，含 token 失效）、`expire_date` 到期自动禁用；可选与 HIS 人事同步。
- 叫号器与后台同一套 `users` 密码（BCrypt），适用 `PWD_POLICY`（§5.4/§9.14）。

## 23.4 会话与登录安全（IAM-6）

- 会话：`users.token/token_time`（§9.14），有效期与续期按 `SESSION_POLICY`；登出 `LogOut` 使 token 失效；可选「单端登录」或「多点登录」策略。
- 登录安全：登录日志 `login_log` 全量记录（成功/失败/IP）；可选异常登录提醒（新 IP、非工作时段）；生产建议 HTTPS 与网关限流。
- 预留 SSO（CAS/OAuth2）对接位：`LoginUser` 支持外部认证回调后返回本地 token（设计预留，实现以代码为准）。

## 23.5 数据权限（IAM-4 / IAM-10）

- `users.data_scope` 决定列表/看板/导出接口的行级范围：

| 值 | 范围 | 典型角色 |
|----|------|----------|
| 1 | 仅本人 | 医生（个人队列） |
| 2 | 本科室 | 科室医生/护士 |
| 3 | 本诊区 | 分诊台护士 |
| 4 | 本院区 | 院区主任 |
| 5 | 全院 | 院长/超管/信息科 |

- `users.campus_scope`：空 = 全院；否则逗号分隔 campus_id；多院区时 `data_scope` 与院区范围取交集生效（见差距分析附录 A §A.8）。
- 所有查询/看板/导出接口按生效范围过滤；越权请求返回业务失败。
- **日志查看权限（L-7，日志补全）：** 日志查询/导出接口同样按 `data_scope`/`campus_scope` 过滤——护士看本科室、科主任看本科室、医务/院长看全院；`sys_action_log` 中管理类操作（清队列、用户/权限变更）仅 ADMIN 可查。

## 23.6 审计与敏感操作（IAM-8）

- 登录审计：`login_log`（§9.19）。
- 敏感操作清单：清队列、停诊/恢复、转诊、插队、改号/调序、改规则/配置、改用户/角色/权限、重置密码。执行即写 `sys_action_log`（§9.19）并可检索；`patient_flow_log`/`nurse_action_log` 保留业务侧留痕（§4.6、§9.19）。
- **访问/导出审计（L-1，日志补全）：** 患者/规则/日志数据的查询与导出统一写 `data_access_log`（谁、何时、查/导出了什么、多少条、IP），满足等保三级与个保法访问留痕。
- **接口与异常日志（L-2，日志补全）：** 接口访问日志（method、path、user_no、code、耗时、ip）与异常堆栈（traceId）落库或对接日志平台（ELK/Loki），属运维审计域。
- **留存与归档（L-5，日志补全）：** 按月归档至 `*_log_archive`，清理按 `LOG_RETENTION`（§10.3，登录 ≥1 年、业务 ≥3 年，可按院规调整）；归档只读可查。
- **等保合规（L-6，日志补全）：** 审计留存 ≥6 个月（建议按上述更长）、日志只追加防篡改（仅 insert，删除需审批）、审计数据与业务库隔离（可选）。
- 导出需按数据权限审批（见差距分析 §18 F-18-2/18-3）。

## 23.7 账号模型与权限演进（设计项）

**现状模型（代码事实）：** 登录信息统一在 `users`（BCrypt）；`Doctor/Login` 优先校验 `users`，无医生档案的窗口岗位登录时补最小 `doctor` 行供绑窗；`doctor.password` 废弃。`login_scene` 约束客户端（管理后台 / 护士站 / 叫号器互斥）。`doctor` 表承担档案与坐诊绑定。

**目标模型（已决策）：** 所有人员（医生、护士、药房、检验、医技/体检、后台）**登录信息统一在 `users` 表**，单一密码方案（BCrypt，适用 `PWD_POLICY`），统一管理（启停、改密、审计 `login_log`、数据权限）。**不做双密码**：`doctor` 表不再承担登录与密码，退化为「医生档案扩展」（职称/专长/排班/诊室）。落地以代码为准。

**1. 现状问题与演进方向**

| 问题 | 说明 | 演进方向 |
|------|------|----------|
| 身份割裂 | 医生登后台 + 登叫号器需两个账号，职称/科室两表各存一份 | `users` 统一身份，`doctor` 退化为档案扩展 |
| 双密码口径 | `users` BCrypt vs `doctor` 明文 | 密码策略收敛到 `users`（`PWD_POLICY`） |
| 审计盲区 | 叫号器 `Doctor/Login` 是否写 `login_log` 未明确 | 医生登录同样写 `login_log`（`scene=DOCTOR`） |
| 语义冗余 | `users.login_scene=DOCTOR` 与 doctor 表登录并存 | 澄清语义（见 §9.14）：`DOCTOR` = 该账号可登叫号器（统一认证入口） |
| 权限模型割裂 | 医生端扁平、无角色/按钮权限 | 见下文「医生端权限精细化」 |

**2. 收敛方案（分阶段，按已决策目标执行）**
1. `doctor` 表密码废弃：`doctor.password` 不再作为登录依据，存量明文迁移比对后清除（**不做双密码**）；
2. 叫号器登录改走 `users`：`Doctor/Login` 兼容期内内部映射到 `users` 校验（工号 + BCrypt），迁移完成后前端直接走统一登录；登录一律写 `login_log`（`scene` 按岗位）；
3. `doctor.user_no` 关联 `users`：同人同号，启停/改密/审计联动；
4. 收敛后：`users` 为**唯一登录信息源**（密码、启停、审计、数据权限、`PWD_POLICY`），`doctor` 表只存档案；`login_scene` 六值在 `users` 语义闭环（见 §23.8）。

**3. 医生端权限精细化**
- 现状：医生站「登录即上岗」，呼叫/重呼/过号/完成/点名/暂停等操作无角色/按钮级控制（§15.2）；
- 设计：医生端挂「岗位角色」或复用 `sys_button_permission`（perm_code 如 `station:pause`、`station:point_call`），由医生管理（§14.7）或角色分配；仅授权医生可用对应操作；
- 数据隔离保持现状：队列按 `doctor_id` + 排班自然隔离，医生端**不需要** `data_scope`（只看自己的队列是硬约束）；
- 多科室出诊需在叫号器切换队列：用 `GetDocCallList.deptId` 切换（已有），可选显示其全部出诊科室入口。

**4. 一致性：** 与 IAM-1～11（§23.2–23.6）、`users_roles` 多角色（IAM-3）一致；医生端岗位角色可复用同一多角色模型。

## 23.8 岗位登录映射与统一（已决策）

**原则：** 所有人员登录信息统一在 `users` 表；登录端由 `login_scene` 决定；窗口岗位的操作模式（`stationMode`）由**上岗绑定的窗口/科室 `business_type`** 决定，不依赖登录人所属档案表。

**1. 岗位登录映射（目标模型）**

| 岗位 | 登录端 | users.login_scene | 模式/范围 |
|------|--------|-------------------|-----------|
| 医生（门诊诊室） | 叫号器 WPF | `DOCTOR` | `CLINIC`（绑定诊室 businessType） |
| 药房窗口人员 | 叫号器 WPF | `PHARMACY` | `PHARMACY` |
| 检验窗口人员 | 叫号器 WPF | `LAB` | `LAB` |
| 医技/体检检查室人员 | 叫号器 WPF | `EXAM` | `EXAM` |
| 护士 | 护士站 Web | `NURSE` | 本诊区（dept_id + data_scope） |
| 后台管理员/主任 | 管理后台 Web | `ADMIN` 等 | 角色菜单 + data_scope |
| 患者 | 签到机 / 体检 H5 | 无 | — |

**2. `login_scene` 语义闭环（users 内）**
- `ADMIN`：可登后台（角色菜单决定范围）；
- `DOCTOR` / `PHARMACY` / `LAB` / `EXAM`：可登叫号器（同一客户端），`stationMode` 由**上岗绑定窗口的 `office_room.business_type`** 决定（而非登录时按科室猜）；同一账号跨岗位（如药师兼检验窗口）需多场景授权；
- `NURSE`：可登护士站；
- 一人多岗位：经 `users_roles`（IAM-3）或 `login_scene` 集合授权。

**3. 与现有字段的关系**
- `users`：`user_no`（工号唯一）、`pass_word`（BCrypt，**唯一密码**）、`login_scene`、`role_id` + `users_roles`、`data_scope`/`campus_scope`、`must_change_password`、`state`、`token/token_time`；
- `doctor`：仅档案（`id`/`work_no`/`name`/`title`/`dept_id`/`specialty`…），`password` 字段废弃、`user_no` 关联 `users`；
- `Doctor/Login` 接口保留为兼容别名，内部校验 `users`。

**4. 一致性：** 与 §23.7 目标模型、差距分析 B.6（IAM-13）、`PWD_POLICY`、`login_log`（§23.3/23.4）一致。

# 24. 现场实施、构建与部署

## 24.1 基础设施建议

- 应用节点：4 核 8G，JDK 17，Nginx。
- 数据节点：8 核 16G，MySQL 8 + Redis。
- 库名 `pdjh`，`utf8mb4`，`lower_case_table_names=1`。
- 密码一律环境变量：`DATASOURCE_URL` `DB_USERNAME` `DB_PASSWORD` `REDIS_HOST` `REDIS_PASSWORD` `SERVER_PORT` 等。
- JVM 示例：`-Xms2g -Xmx4g --spring.profiles.active=prod`。

本地可 `docker compose -f docker-compose-infra.yml up -d` 再启动 `mvnw spring-boot:run`。

## 24.2 构建前端

仓库根：`npm run build:frontends`。产物：

- 大屏 `HJ候诊区大屏/dist` → nginx `.../html/screen/`
- 门边屏 `HJ诊室门边屏终端/dist` → `clinic/`
- 签到 `HJ自助签到终端/dist` → `checkin/`
- 护士 `HJ护士工作站/dist` → `nurse/`
- 体检 `HJ体检H5/dist` → `checkup/`
- 后台 `HJ管理后台/Gocent.Manager/dist` → `admin/`（注意 `publicPath` 与 location 一致）
- 官网直接拷贝静态文件

Nginx `location /api/` 必须 `proxy_http_version 1.1` 且 Upgrade，超时加长（3600s），`proxy_pass` 要保留后端 `/api`（后端 context-path 就是 `/api`）。

## 24.3 桌面端

叫号器用 VS 编安装包分发。音响 `dotnet publish -r win-x64 --self-contained`。配置文件里的 API 指向院内地址。

## 24.4 推荐实施顺序

1. 起库与 Redis，启动后端，确认 `/api/System/GetDataTime`。
2. 导入种子或实施向导走完库检查。
3. 建诊区树 → 物理诊室 → 医生与排班。
4. 配规则中心四条业务线。
5. 注册屏幕/签到机/音响并绑定诊室。
6. 配 SCREEN_CFG / CLINIC_CFG。
7. 装壳，长按填服务根，走绑定直到 READY。
8. Mock HIS 或真 HIS 推一条号，签到 → 医生叫号 → 大屏/门边屏/音响联动。
9. 护士代签、过号复活走一遍，查患者流程日志。
10. 主任台看是否有数。验收实施任务全部 finish。

## 24.5 UAT 建议清单（每条附期望断言）

- 门诊：预约过早拒绝、迟到降权、顺呼、重呼、过号三次 PASSED、复诊优先。
  - 期望：过早（>30 分钟常量）签不到 → 拒绝并提示时段；迟到超宽限 → 签成功且 `is_appointment` 1→0；顺呼取队首；重呼同单再播；**过号三次 → triage=PASSED 且 call_count=3**；复诊回流单优先于普通等候。
- 药房：签到 PREPARING 不可叫，MarkReady 后可叫。
  - 期望：扫码建单 → `PREPARING` 且 `AutoCallNext` 拒绝；`pharmacyMarkReady` → `WAITING` 后窗口可叫；叫号后无人取药按 `callTimeoutMin` 口径处理（§10.1，以代码为准）。
- 检验：分窗、无 HIS 单也能建单。
  - 期望：扫码自动分到最短队列窗口；无 `UNARRIVED` 预推单时 `labCheckIn` 新建单直接 `WAITING`。
- 体检：空腹优先、依赖阻断、挂起重算、H5 改签。
  - 期望：早高峰下一站优先空腹项；`depends_on_ids` 未完成项不出现在下一站；科室挂起后自动绕开并重路由；H5 改签不破坏依赖约束。
- 终端：错壳提示、冻结待机、脱敏、音响与大屏通道切换。
  - 期望：SCREEN 壳进 CLINIC 设备 → `/wrong-terminal`；冻结设备只显待机原因；姓名默认 `张*三`；`voice_channel` 由 VOICE 切 SCREEN 后大屏本机出声。
- 权限：无菜单角色无法进后台；停用账号无法登录。
  - 期望：无 `sys_role_menu` 授权 → 登录失败“未配置菜单”；`users.state=0` → 拒绝登录并提示。
- **幂等（P1-3，联调必测）**：同一 HIS 推送/同一扫码重复调用 `enqueue`/`signIn` → **不产生重复单、不重复扣减**（现状是否判重以代码为准；未判重则按 §4.2/§11.1 口径在集成层去重）。

## 26.5 术语

| 术语 | 含义 |
|------|------|
| 诊区 | department 树节点 |
| 物理诊室 | office_room，门牌位置 |
| 排队单 | call_list |
| 设备编号 | device_code，壳指纹或手填 |

| 复活 | 过号单回到可叫 |

**SLA 计时口径表（P1-1，建议口径，落地以代码为准）：**

| 场景 / triage_state | 是否计入等候 SLA | 说明 |
|--------------------|------------------|------|
| `UNARRIVED`（7，未签到） | 不计 | 等候从签到起算 |
| `WAITING`（0，已签到） | 计 | 起点 `check_in_time` |
| 就诊中（1） | SLA = `start_time` − `check_in_time`（术语表原口径） | 到首次叫号接诊止 |
| 过号重排（未达上限回 `0/WAITING`；达上限 `6/PASSED`→复活回 `0`） | 建议**累计不重置** | 若现场要求“按到号应答时长”，以配置/代码为准 |
| `REVISIT` 复诊回流 | 独立计次 | 以该次签到/入队时间重新起算 |
| `TESTING` 去检查暂离 | 不计（或单列口径） | 暂离期间冻结计时（§11.2） |
| 药房 `PREPARING`（配药中） | 不计排队 SLA | 配药时长单独看；`WAITING` 起计入取药等候 |

> 统计侧 P50/P90、最长候诊（R-11）基于上述单次等候区间；精确规则以代码为准并回填本表。
