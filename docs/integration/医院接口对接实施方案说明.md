# 欢匠·序流排队分诊管理系统 - 医院接口对接实施方案说明

> **文档位置：** `docs/integration/` · 对接模式或配置变更请同步更新本文档。

本说明文档旨在为现场实施工程师及医院信息中心（IT部门）提供系统对接的标准作业程序（SOP）。针对国内各级医疗机构异构的 IT 基础设施现状，欢匠·序流系统底层核心（`pdjh-server`）内置了**多协议异构综合中台网关 (Integration Gateway)**，提供下述四种标准对接融合方案。

实施团队入场后，请首先与院方信息中心评估现有信息系统（HIS/LIS/PACS等）的开放能力与网络安全策略，选择最契合当前院情的方案进行高效对接。

---

## 方案一：主动调用模式 (HTTP Active Integration)

**【适用场景】**
新建院区、大型三甲医院，或院内已建成统一且规范的微服务总线 / 医院信息集成平台。医院可提供标准化的 RESTful / SOAP 接口服务及相应的 API 接口说明文档。

**【运作机制】**
排队系统作为**服务消费方 (Consumer)**，遵循院方接口规范，主动向医院集成平台发起数据获取请求。

**【实施步骤】**
1. **网络白名单互通**：确保排队应用服务器（节点 A）的 IP 能够被院方 API 网关放行并正常通信。
2. **鉴权凭据申请**：向院方申请调用接口所需的认证凭据（如 AppKey / AppSecret 或 JWT Token）。
3. **网关服务配置**：在引擎配置文件 `application-prod.yml` 中激活主动调用模式，并配置目标 URL：
   ```yaml
   integration:
     mode: http_active
     his-api-url: http://api.hospital.local/v1
   ```
4. **适配器映射配置**：通过系统后台或配合研发支持，在适配器组件 `HttpActiveIntegrationImpl.java` 中录入真实的业务字段提取与映射规则。

**【优缺点评估】**
* **优点**：架构最为标准现代、耦合度低。排队系统具备数据获取节拍的自主控制权，易于实现错误重试。
* **缺点**：直接依赖院方 API 平台的可靠性与响应速度；若院方接口响应延迟，可能会在签到等高频业务点引起短暂偶发卡顿。

## 方案二：事件回调模式 (Passive Webhook)

**【适用场景】**
各独立医技辅助科室（如 LIS 检验科、RIS 影像科）。这些独立的第三方专科系统通常难以配合排队系统进行主动接口开发，但其原生具有业务节点流转时的“对外消息广播 (Webhook / MQ)”的能力。

**【运作机制】**
排队系统作为**服务提供方 (Provider)**，开放标准 HTTP 接收端点，被动接收第三方系统在特定事件（如“检查完毕”）发生时推送的状态报文。此模式多用于 **“检查状态扭转触发算路”**。

**【实施步骤】**
1. **标准接口暴露**：向院方或第三方检验系统实施方提供我方的标准 Webhook 接口技术规范：
   * 接口地址：`http://[排队服务器IP]:8080/api/integration/webhook/exam/status`
   * 必须入参：`patientCode` (患者条码/就诊卡号), `itemCode` (检查项目代码), `state` (业务流转状态，如 4 代表执行结束)。
2. **中心网关配置**：在引擎配置文件 `application-prod.yml` 中激活被动接收模式：
   ```yaml
   integration:
     mode: passive_receive
   ```
3. **安全防护策略**：通过 Nginx 或系统内部安全模块，严格配置调用此接口的 IP 白名单，防止内网的恶意无效请求。

**【优缺点评估】**
* **优点**：业务流转实时性极高；患者完成检查（如采血结束）的瞬间，系统即可响应并触发候诊及大屏联动，即刻指引前往下一科室。
* **缺点**：实施过程中需协调第三方系统厂商（如 LIS/PACS 供应商）配合进行少量的数据推送改造。

## 方案三：数据视图直通模式 (JDBC Polling)

**【适用场景】**
适用于仍在使用传统单体直连 HIS 系统，且医院信息中心因预算、人力或厂商维保原因**无法开辟 HTTP RESTful 接口**的场景。

**【运作机制】**
系统作为**异构数据读取方**，利用标准的 JDBC 驱动，在安全且极度受控的前提下，直连医院后台 Oracle 或 SQLServer。

**【实施步骤】**
1. **建立安全读取边界**：严禁采用具备写入权限的账号直连核心业务表。需向院方 DBA 申请一个只读（Read Only）数据库账号，并在 Oracle / SQLServer 中创建一个**安全只读视图 (View)** 或由系统层维护的 **定时中间同步表**。（注：视图范围内仅暴露当日必要的挂号与就医事件字段）
2. **双数据源挂载**：在 `application-prod.yml` 中启用 JDBC 模式，并配置次级数据源的直连信息：
   ```yaml
   integration:
     mode: jdbc_polling
   spring:
     datasource:
       his:
         driver-class-name: oracle.jdbc.OracleDriver
         url: jdbc:oracle:thin:@10.0.0.8:1521:orcl
         username: RO_QUEUE_USER
         password: xxxx
   ```
3. **轮询适配器调度**：系统内部的调度组件 `JdbcPollingIntegrationImpl.java` 会启动基于增量时间戳（游标）定时查询机制（默认频率 3-5 秒）。若探测到视图中新增挂号或收费凭证记录，即刻同步至本地排队业务队列表。

**【优缺点评估】**
* **优点**：能够绕过由于接口定制受阻造成的集成僵局，只要院方能开放基础的只读视图查询权限，即可极速打通核心数据流，是保证项目快速交付的有效手段。
* **缺点**：属于平台非标准解耦方案；若院方底层核心表结构发生非预期业务变更容易导致同步中断；且轮询动作对院方数据库有细微的只读查询开销。

## 方案四：边缘网关隔离代理模式 (Edge Agent Proxy)

**【适用场景】**
针对具备极为严苛的信息安全隔离策略，且**明确禁止在核心业务防火墙内向外系统开放“对内入站 (Inbound)”端口**的特殊内网机房环境。

**【运作机制】**
提供一款基于 Go/Rust 跨平台编译的极轻量级、无环境依赖的可执行跨网探针（Edge Agent）。将其部署于医院具有部分出站（Outbound）网络访问权限的边界主机上。由探针在内网局部安全区域完成读库行为，并通过加密 HTTPS 长连接 **主动向上游** 汇报数据，从而符合不出站的安全红线规范。

**【实施步骤】**
1. 获取编译发行的隔离探针可执行文件 `pdjh-edge-agent`。
2. 部署于院内安全审批许可的主机，并在同目录配置 `config.yaml` 录入使用 JDBC 读取内网视图的加密凭证。
3. 指定其向上游云端或主排队系统推送状态同步的 Webhook URL。排队系统核心服务全程无需对外暴露网络入站侦听接口。

## 五、 实施增效与联调工具箱 (Productivity Tools)

为大幅缩短实施专员的驻场联调周期与环境试错成本，管理后台集成了三大敏捷适配工具链：

1. **统一适配模板管理中心 (Integration Marketplace)**：简化手工梳理字段映射的工作。当识别出院方 HIS 属于行业主流提供商（如卫宁、东软、创业等架构表）时，实施专员可使用模板直导，系统即可生成标准的 API 请求报文规范及对应的 JSONPath 规则表达解析树。
2. **联调测试沙盘 (Dry-Run Box)**：实施工程师可以在免中断核心业务运行的情境下，将提取得到的非标准 JSON 报文范本置入后台系统沙盘以匹配相应的 JSONPath 规则。工作台提供实时模拟演绎结果对齐，有效规避由于反复调试触发的重启成本。
3. **配置级版本控制与安全回读 (Git for Configs)**：对系统在现场的所有通信参数与报文提取逻辑映射修改，系统自带底层快照版本追溯轴；若由于参数错配等因素而发生运行异常，实施人员随时调用“快照历史”功能实现精准的配置版本秒级无感回滚。

## 附：集成网关实施决策沟通树

在现场面对医院信息管理部门推进技术对接需求时，项目责任经理可参考下辖分级决策机制实现降维切入沟通：

1. `"贵院是否有统一的临床数据集成总线或 API 生态体系？是否有标准成熟的接口服务（我们具备标准模板导入能力）？我方系统支持按需主动调取结构化报文以促成数据握手同步。"` **(→ 推荐：采用 方案一 主动调用模式)**
2. 若暂无总线平台或定制成本无法短期承受：`"那么贵院涉及信息模块抑或检验第三方子系统环境是否具备支持外发的 HTTP / MQ 事件广播机制能力？如果开放许可，排队系统备妥外部 Webhook 事件接收节点。"` **(→ 推荐：采用 方案二 事件回调模式)**
3. 若遭遇定制系统研发阻塞且无能力处理外部推送回调的阻力：`"为在零代码侵入的前提下降低贵方代码体系被干扰风险，信息中心或可特许在旧有数据库层面分配一个仅供挂号抽取的只读视图（View）脱敏账号？转换机制与异常容错控制统筹交由我方业务枢纽接管内化。"` **(→ 推进采用 方案三 数据视图直通模式)**
4. 若遭逢严格的信息物理硬隔离等不可突破的网络安全反弹：`"面对严令禁止对外对内网双向入站端口监听的安全红线法则，为彻底杜绝内网数据遭入侵风险，我们提议将数据抓取组件单向化隔离探针化（Edge Agent），只允许内部探针向上网边界发出被动推送协议的数据包。"` **(→ 推进采用 方案四 边缘网关隔离代理模式)**
